## 不能出错的软件 {#why}

大多数软件错误只是让人烦恼：应用崩溃了，重启一下，损失几分钟而已。但有些软件在驾驶飞机、控制放射剂量、运行列车、转移资金或守护机密。在这些地方，一个错误可能让人付出生命或巨额财富的代价，等到事后才发现就太晚了。下面三个有据可查的事故说明了其中的利害。

- **阿丽亚娜 5 号，1996 年。** 首次发射后不到一分钟，火箭偏离航线并解体。它的制导软件沿用自速度较慢的阿丽亚娜 4 号，其中有一处把 64 位浮点数转换成 16 位整数。在新火箭上，这个值超出了 16 位整数的范围，转换失败，而这次失败让两套惯性参考装置——主装置和与它完全相同的备份装置——都停止了工作。
- **Therac-25，1985–1987 年。** 一台放射治疗机让六名患者受到严重过量的照射，其中至少三人死亡。原因之一是控制软件中的竞态条件（race condition）：操作员如果快速修改治疗参数，就可能让机器处于致命的配置，而早先的型号是用硬件联锁装置来防止这种情况的。
- **奔腾 FDIV 错误，1994 年。** 英特尔的新处理器在做某些除法时结果出错，原因是除法电路的一张表里缺了几个表项。更换芯片让英特尔付出了 4.75 亿美元。从那以后，芯片厂商一直用定理证明器来验证它们的运算单元。

在这几个例子中，系统都经过了测试，而测试漏掉了错误。艾兹格·迪杰斯特拉（Edsger Dijkstra）在 1970 年用一句话说出了原因：“程序测试可以用来表明错误的存在，却永远不能表明错误的不存在。”

算一笔小账就能看出为什么。一个接受两个 64 位整数的函数有 $2^{128}$ 种、约 $3.4 \times 10^{38}$ 种可能的输入。即使每秒测试十亿个，也需要大约 $10^{22}$ 年才能全部试完，差不多是宇宙年龄的一万亿倍。测试只是在这个空间里抽样，不可能把它覆盖完。

还有另一条路：用数学描述程序必须做什么，然后**证明**它对每一个输入都做到了。这就是形式化方法背后的思想，而且它已经在工业规模上取得了成功。

- **seL4** 是一个操作系统微内核。2009 年，人们证明了它的 C 代码实现了它的规约，证明由 **Isabelle/HOL**（也就是本系列讲授的系统）进行机器检查。它是第一个拥有这种证明的通用内核。
- **CompCert** 是一个在证明助手 Rocq（原名 Coq）中证明正确的 C 编译器。2011 年，研究人员用随机生成的程序测试 C 编译器，在 GCC 和 LLVM 中发现了许多导致生成错误代码的缺陷，而在 CompCert 经过验证的部分中一个也没有找到。
- **亚马逊云服务**（Amazon Web Services）的工程师从 2011 年起就用 TLA+ 语言为 S3、DynamoDB 等系统编写规约，并用模型检测器检查它们。检测器找到了一些隐蔽的设计错误，其中一个需要 35 步的事件序列才能展示出来。
- **巴黎地铁 14 号线**自 1998 年开通以来一直无人驾驶。它的安全关键软件是用 B 方法开发和证明的。

形式化方法需要时间和专业知识，所以它们被用在失败代价更高的地方：航空电子、铁路、医疗设备、处理器、操作系统内核、编译器、密码协议。这些领域的标准也承认它们：航空电子标准 DO-178C 有一份形式化方法补充文件 DO-333，而信息安全评估的通用准则（Common Criteria）的最高等级 EAL 7 要求经过形式化验证的设计。

## 怎样才算“形式化” {#formal}

日常语言适合交谈，却不适合写规约。看一条来自学校软件的需求：“打印成绩列表之前，先把它排好序。”从高到低还是从低到高？两个相同的分数怎么处理？还有一个不那么明显的问题：排序函数可以返回空列表吗？空列表当然是有序的。没有人会故意写出这样的函数，但这句话里没有任何东西禁止它，而一个会丢失成绩的程序，正是那种容易漏网的错误。

**形式化**方法用三样东西消除这种含糊：

1. **形式语言**，有精确的语法，使每个陈述只有一种读法。
2. **语义**，用数学定义每个陈述的含义以及它何时为真。
3. **证明系统**，一套一步一步推导真陈述的规则，规则简单到计算机可以检查每一步。

::: definition 形式化方法
**形式化方法**（formal method）是用一种具有精确数学含义的语言来描述或验证系统的方法，这样关于系统的断言就可以通过计算或证明来检查，而且往往由计算机来检查。
:::

在这样的语言里，排序需求变成了关于输入列表 $xs$ 和输出列表 $ys$ 的两个条件：

$$
\mathit{sorted}(ys) \;\land\; \mathit{mset}(ys) = \mathit{mset}(xs)
$$

读作“$ys$ 是有序的，**并且** $ys$ 与 $xs$ 含有相同的元素，每个元素出现的次数也相同”。符号 $\land$ 表示“并且”；$\mathit{mset}$ 把一个列表变成由它的元素组成的多重集（multiset，也叫袋），不计顺序。第二个条件正是那句话遗漏的：它排除了丢失、增加或重复成绩的情况。你会在模块 2 和模块 3 学习读写这样的公式；现在只需注意，写出规约迫使我们做出了那句话没有做出的决定。

::: definition 规约
**规约**（specification）是对系统必须做**什么**的精确陈述，而不说明**怎样**做。**形式化规约**用形式语言写成。
:::

::: definition 验证与确认
**验证**（verification）表明一个实现满足它的规约。**确认**（validation）检查规约描述的是否正是真正想要的东西。巴里·玻姆（Barry Boehm）的概括是：验证问的是“我们是否在正确地构建产品？”，确认问的是“我们构建的是否是正确的产品？”。
:::

::: figure id=fig-01-1
形式化方法位于需求与程序之间。确认把需求和规约联系起来；验证把规约和实现联系起来。
:::

::: keyidea
一个测试只说明一个输入的情况，一个证明则说明每一个输入的情况。但证明只能表明程序满足它的**规约**：如果规约错了，你证明的就是错误的东西。确认仍然重要。
:::

::: pitfall
“经过验证”从来不意味着无条件的“正确”。它的意思是**相对于某个规约**、**在某些假设之下**是正确的：假设编译器、硬件和环境模型的行为都与描述一致。这些假设，加上证明检查器本身，构成了**可信基**（trusted base）。清楚它包含什么，是用好形式化方法的一部分。
:::

## 形式化方法全景 {#landscape}

形式化方法是一个大家族。它们的区别在于能表达多少、能自动完成多少，以及给你什么样的结果。测试不是形式化方法，但它是比较其他各种方法时的基准。

| 方法 | 你提供 | 它做什么 | 你得到 | 局限 | 例子 |
|---|---|---|---|---|---|
| 测试 | 输入和预期输出 | 运行程序 | 你所选输入上的错误 | 不能表明错误不存在 | 单元测试；基于性质的测试（QuickCheck、Hypothesis） |
| 模型检测 | 系统的有限模型和一条性质 | 遍历每一个可达状态 | “成立”，或一条反例轨迹 | 状态数会爆炸；模型必须有限或经过抽象 | SPIN、NuSMV、TLA+ 的 TLC、UPPAAL |
| SAT 与 SMT 求解 | 关于布尔值、数、数组或位向量的公式 | 自动判定它能否被满足 | 一个满足它的赋值，或“不可满足” | 很多问题不可判定或太难：可能放弃 | MiniSat、CaDiCaL、Z3、cvc5 |
| 交互式定理证明 | 用表达力强的逻辑写出的定义、定理和证明，借助自动化完成 | 检查每一个证明步骤 | 在每种情况下都成立的定理，包括无穷多种情况 | 需要人的努力和技能 | Isabelle、Rocq、Lean、HOL4、ACL2 |

从表中可以看出两点。第一，这些方法在表达力和自动化之间取舍。SAT 求解器能自己给出答案，但只针对有限的、规模固定的问题；定理证明器可以陈述“一个编译器对所有可能写出的程序都正确”，但需要你的引导才能证明它。第二，这些方法可以结合。Dafny 和 Frama-C 这样的程序验证器把程序转换成公式交给 SMT 求解器。而你将看到，Isabelle 内置了一个测试工具（**Quickcheck**）、一个反例搜索器（**Nitpick**，它使用 SAT 求解器），以及一座通往自动定理证明器和 SMT 求解器的桥梁（**Sledgehammer**，它会调用 Z3、cvc5 等），所有这些都由同一个小内核来检查。

::: note
为什么计算机不能直接判定任意陈述的真假？因为不存在这样的算法：艾伦·图灵（Alan Turing）在 1936 年证明，没有程序能够对每个程序和输入判定它是否会停机；在此之前，库尔特·哥德尔（Kurt Gödel）已经证明，没有哪个证明系统能证明关于算术的所有真理。所以对于表达力强的逻辑，一定程度的人工引导是不可避免的。模块 3 会再谈这个问题。
:::

## 证明助手，以及为什么可以信任它们 {#trust}

**证明助手**（proof assistant），又称交互式定理证明器，是一种程序：它检查用形式逻辑写成的证明，并帮助你找到证明。可以把它想象成一位同事，他会读你证明的每一行，从不疲倦，也从不放过任何漏洞；身边还有一队助手，能帮你补上常规的步骤。

但证明助手本身也是一个大程序。Isabelle 有几十万行代码。凭什么要比信任被它检查的软件更信任它？答案是罗宾·米尔纳（Robin Milner）在 20 世纪 70 年代为爱丁堡 LCF 系统（Logic for Computable Functions，可计算函数逻辑）发明的一种架构，Isabelle 和许多其他证明器都采用了它。

::: definition LCF 方法
在 **LCF 风格**的证明器中，定理是一个抽象类型 `thm` 的值。唯一能创建这种类型的值的函数，实现的正是逻辑的推理规则。它们组成一个小小的**内核**（kernel）。系统的其他任何部分，无论多么巧妙，都必须调用内核才能构造出定理。
:::

::: figure id=fig-01-2
LCF 架构。证明工具可以很大，也可以有错误，因为它们产生的每个定理都是由内核的规则构造的。
:::

因此，化简器、自动证明器以及其他所有工具都在可信基之外：如果其中某个工具有错误，证明可能失败或永远运行下去，但错误的陈述不可能变成定理。只有内核必须正确，而它小到可以被非常仔细地检查。米尔纳还设计了一种编程语言 ML（“Meta Language”，元语言），用来安全地编写这类工具；Isabelle 至今仍然用 ML 和 Scala 编写。

**Isabelle** 由劳伦斯·保尔森（Lawrence Paulson）于 1986 年在剑桥大学开始开发，最初是一个**通用**证明助手：一个可以定义多种逻辑的框架。托比亚斯·尼普科（Tobias Nipkow）和他在慕尼黑工业大学的团队开发了 **Isabelle/HOL**，也就是几乎所有人都在用的那个逻辑；马卡里乌斯·文策尔（Makarius Wenzel）创建了 Isar 证明语言和证明器集成开发环境 Isabelle/jEdit。HOL 代表**高阶逻辑**（higher-order logic）：一种带类型的逻辑，其中函数和其他东西一样是值，很接近一门加上了逻辑的函数式编程语言。本系列自始至终使用 Isabelle/HOL；下文中的“Isabelle”都指 Isabelle/HOL。

Isabelle/HOL 曾用于 seL4 的证明、开普勒猜想证明的一部分（与 HOL Light 一起），以及**形式化证明档案库**（Archive of Formal Proofs）中的数百个项目——这是一个在线的、经过检查的 Isabelle 证明库。你可能还会遇到的其他证明助手有 Rocq（原名 Coq）、Lean、HOL4 和 ACL2。它们的逻辑和风格各不相同，但本系列中的思想同样适用于它们。

## 安装 Isabelle2026 {#install}

Isabelle2026 于 2026 年 10 月发布，是当前版本。下载包里什么都有：Isabelle/jEdit 编辑器、预先构建好的 HOL 逻辑、自动证明器和手册。你不需要另外安装 Java 或其他任何东西。Isabelle 主页要求做小型实验至少要有 4 GB 内存和 2 个处理器核心，推荐 8 GB 和 4 个核心；本系列的例子都很小。

从 **isabelle.in.tum.de** 下载（主页上的“Download for …”链接），然后按你的系统执行下面的步骤。Isabelle 的界面只有英文版，本系列会在英文标签后面给出中文解释。

:::: tabs
::: tab Windows
1. 下载 **Isabelle2026.exe**（适用于 Windows 10 或 11）并运行它。这是一个自解压文件：选择一个文件夹来解压，例如你的用户主文件夹。
2. Isabelle 没有注册开发者的签名，所以 Windows 一开始会拒绝运行它。如果出现一个蓝色窗口，显示“Windows 已保护你的电脑”（Windows protected your PC），先点击**更多信息**（More info），再点击**仍要运行**（Run anyway）。
3. 安装程序结束后会启动 Isabelle/jEdit，并创建一个桌面快捷方式。以后就用这个快捷方式启动。
:::
::: tab macOS
1. 下载适合你的 Mac 的版本：Apple 芯片（M1 及以后）选 **macOS (ARM)**，否则选 **macOS (Intel)**。如果浏览器没有自动解压，就先解压，然后把 **Isabelle2026.app** 移到**应用程序**（Applications）文件夹。
2. Isabelle 没有注册开发者的签名，所以 macOS 一开始会阻止它。打开 Isabelle2026.app，在安全对话框中点击**取消**（Cancel）。
3. 打开**系统设置 → 隐私与安全性**（System Settings → Privacy & Security）。在靠近底部的地方，有一条消息说 Isabelle2026 已被阻止；点击**仍要打开**（Open Anyway）并确认。之后 Isabelle 就能像其他应用一样启动了。
:::
::: tab Linux
1. 下载 **Isabelle2026_linux.tar.gz**（ARM 电脑则下载 Linux (ARM) 版本），解压到任意位置：

   ```terminal
   $ tar -xzf Isabelle2026_linux.tar.gz
   ```

2. 启动 Isabelle/jEdit：

   ```terminal
   $ Isabelle2026/Isabelle2026
   ```

   你需要一个图形桌面环境。命令行工具在 `Isabelle2026/bin/isabelle`；本系列用不到它们。
:::
::::

第一次启动时，Isabelle/jEdit 会打开你主文件夹中一个名为 `Scratch.thy` 的空理论。等到右边的 **Theories**（理论）面板显示 **Prover: ready**（证明器：就绪），就说明 Isabelle 已经加载了 HOL，可以检查你输入的内容了。

::: trouble
- **Windows：Sledgehammer 或 `smt` 报告某个证明器无法运行。** Windows Defender 可能会阻止 Isabelle 的外部证明器。Isabelle 的安装页面建议在**病毒和威胁防护**（Virus & threat protection）中排除整个 Isabelle 文件夹。在模块 9 之前你用不到这些工具。

- **Isabelle 非常慢，或者因内存不足而停止。** 关闭其他占用内存大的程序。Isabelle 需要上面所说的内存。
:::

## Isabelle/jEdit 导览 {#tour}

你现在打开的这个窗口 Isabelle/jEdit 是一个**证明器集成开发环境**（prover IDE）：在你输入的同时，Isabelle 就在持续检查编辑器中的文本。这里没有“运行”按钮。图 1.3 展示了这个窗口，里面是你马上要写的理论。

::: figure id=fig-01-3 image=jedit-overview.png alt="Isabelle/jEdit 窗口：编辑器中是一个理论，下方打开了 Output 面板，右侧是 Theories 面板，左侧是 Documentation 面板。编号 1 到 5 标出了这些部分。"
Isabelle/jEdit，Linux 上的 Isabelle2026。在 Windows 和 macOS 上，除了窗口边框，看起来都一样。
:::

1. **文本区**，你在这里编写理论。命令按种类着色，左侧的边栏用图标显示消息：蓝色的 **i** 表示信息，红色的 **!** 表示错误。
2. **Output**（输出）面板显示光标所在命令的消息。它一开始是关闭的：点击窗口底部的 **Output** 标签即可打开。
3. **Proof state**（证明状态）。把这个框勾选一次。之后 Isabelle 会在 Output 面板中显示光标处还剩下什么需要证明。这个设置在以后的会话中会被记住。
4. **Theories** 面板显示 **Prover: ready** 以及每个已打开理论的进度。
5. **Documentation**（文档）面板列出 Isabelle 自带的手册。最有用的是 **prog-prove**，即《Programming and Proving in Isabelle/HOL》，本系列第三部分就以它为线索。

从一开始就养成几个习惯会很有帮助。把鼠标悬停在带下划线的文字上，可以看到它的消息。按住 <kbd>Ctrl</kbd>（macOS 上是 <kbd>Cmd</kbd>）并把鼠标悬停在一个名字上，可以看到它的类型和定义；点击则跳转过去。要输入数学符号，就输入下表中的缩写：Isabelle 会把它替换成符号，要么立即替换，要么弹出一个小窗口，在其中按 <kbd>Tab</kbd> 确认。你也可以输入反斜杠加符号的名字，例如 `\forall`，或者在底部的 **Symbols**（符号）面板中点击符号。

| 符号 | 输入 | 含义 |
|---|---|---|
| ⇒ | `=>` | 函数类型 |
| ∧ | `/\` 或 `&` | 并且 |
| ∨ | `\/` 或 <code>&#124;</code> | 或者 |
| ¬ | `~` | 非 |
| ⟶ | `-->` | 蕴涵 |
| ⟷ | `<->` | 当且仅当 |
| ∀ | `\forall` | 对所有 |
| ∃ | `\exists` | 存在 |
| ≠ | `~=` | 不等于 |
| ≤ | `<=` | 小于或等于 |

复制也可以：这些页面上的 Isabelle 文本使用和 Isabelle 相同的 Unicode 符号，所以你可以用代码块的**复制**按钮复制，再粘贴到 Isabelle/jEdit 中。

## 你的第一个理论 {#first}

你在 Isabelle 中写的所有东西都放在一个**理论**（theory）里：理论是一个包含定义、陈述和证明的文件，就像编程语言中的一个模块。现在你将一步一步写出一个理论，并接触 Isabelle 的三种基本活动：计算、证明和反驳。

### 创建文件 {#first-file}

在 Isabelle/jEdit 中选择 **File → New**（文件 → 新建），然后选择 **File → Save As…**（文件 → 另存为）。为本系列建一个文件夹，例如主文件夹中的 `isabelle`，把文件保存在那里，命名为 **`First.thy`**。然后输入：

```isabelle norun
theory First
  imports Main
begin

end
```

`theory First` 给理论命名，这个名字必须与文件名一致：理论 `First` 要放在 `First.thy` 中。`imports Main` 引入标准库：数、列表、集合，以及关于它们的成千上万条已经证明的事实。其余所有内容都写在 `begin` 和 `end` 之间。下面的命令都写在 `end` 之前的新行上。

::: trouble
如果 Isabelle 在 `First` 下面画了下划线，并且提示

```text
Bad theory name "First" for file "Scratch.thy"⌂
```

这条消息的意思是：对文件“Scratch.thy”来说，理论名“First”不正确。也就是说，理论名和文件名不一致。把文件另存为 `First.thy`，或者把 `theory` 后面的名字改成与文件名一致。
:::

### 计算 {#first-compute}

输入这一行：

```isabelle
value "2 + 3 :: nat"
```

把光标放在这一行上。Output 面板会显示结果和它的类型：

```output
"5"
  :: "nat"
```

`value` 对一个项求值。引号里的文本属于 Isabelle 的**内层语法**（inner syntax），即项和类型的语言；而 `value`、`lemma` 这样的命令属于**外层语法**（outer syntax），写在引号外面。`:: nat` 是类型标注：它说明 `2 + 3` 是一个自然数，也就是 0、1、2……中的一个。没有它，Isabelle 不知道你指的是哪一种数，也就无法求这个和。

Isabelle 能计算的不只是数。`rev` 把一个列表反转：

```isabelle
value "rev [1, 2, 3 :: nat]"
```

```output
"[3, 2, 1]"
  :: "nat list"
```

::: trouble
如果去掉类型，Isabelle 会拒绝：

```isabelle fails
value "2 + 2"
```

```output
*** Wellsortedness error:
*** Type 'a not of sort term_of
*** Cannot derive subsort relation numeral < term_of
```

这条消息很难懂，但解决办法很简单：加上类型标注，例如 `:: nat` 或 `:: int`。你会在模块 8 学习如何读懂这类消息。
:::

### 证明 {#first-prove}

现在来看一个关于所有列表的断言：把一个列表反转两次，会得到原来的列表。输入这个陈述：

```isabelle
lemma "rev (rev xs) = xs"
```

变量 `xs` 没有在任何地方定义过。Isabelle 把它看作代表**任意**列表，所以这条引理断言该等式对每个列表都成立。勾选了 **Proof state** 之后，Output 面板会显示**目标**（goal），即仍有待证明的陈述：

```output state
proof (prove)
goal (1 subgoal):
 1. rev (rev xs) = xs
```

现在来证明它。在下一行输入：

```isabelle
  by simp
```

目标消失了，也没有任何报告：证明被接受了。`simp` 是**化简器**（simplifier），它用已知的等式重写目标，直到目标变成 `True`。这里，库中已经包含了 `rev (rev xs) = xs` 这一事实。Isabelle/jEdit 甚至会告诉你这一点：引理旁边边栏里的蓝色 **i** 带着一条消息“Auto solve_direct: the current goal can be solved directly with List.rev_rev_ident”（自动 solve_direct：当前目标可以直接用 List.rev_rev_ident 解决）。在幕后，`simp` 是通过调用内核的规则来构造这个定理的，正如第 1.4 节所描述的。

### 定义与证明 {#first-define}

现在定义一个你自己的函数。`fun` 用等式来定义函数：

```isabelle
fun double :: "nat ⇒ nat" where
  "double n = n + n"
```

```output
consts
  double :: "nat ⇒ nat"

Found termination order: "{}"
```

`double :: "nat ⇒ nat"` 声明 `double` 接受一个自然数并返回一个自然数；输入 `=>` 就能得到符号 ⇒。`where` 后面的等式说明 `double` 计算什么。Isabelle 的回答给出了新常量和它的类型，并报告它找到了一个终止序（termination order）：对每个用 `fun` 定义的函数，Isabelle 都会证明它会终止。这里没有递归，所以证明是平凡的；模块 8 会解释为什么终止性很重要。现在试一试这个函数：

```isabelle
value "double 21"
```

```output
"42"
  :: "nat"
```

不过，一次测试只能展示一个值。下面是一个关于每个 `n` 的断言，以及它的证明：

```isabelle
lemma "double n = 2 * n"
  by simp
```

化简器使用 `double` 的定义等式（`fun` 会自动登记它）和算术定律。把光标放在引理那一行上就能看到目标，如图 1.4 所示。

::: figure id=fig-01-4 image=jedit-state.png alt="光标位于 lemma double n = 2 * n 这一行。Output 面板中的 Proof state 框已勾选，面板显示：proof (prove)，goal (1 subgoal)，1. double n = 2 * n。"
勾选 **Proof state** 后，Output 面板显示光标处的目标。
:::

### 反驳 {#first-refute}

如果一个断言是错的呢？试试这个：

```isabelle
lemma "double n = n * n"
```

不到一秒钟，这一行旁边就会出现一个蓝色的 **i**。把光标放在这一行上（图 1.5）：Isabelle/jEdit 已经自动用 **Quickcheck** 在一些较小的值上试过这个断言，并找到了一个使它不成立的值。你也可以自己运行 Quickcheck，本系列的理论文件就是这样做的：

```isabelle
  quickcheck
```

```output result
Testing conjecture with Quickcheck-exhaustive...

Quickcheck found a counterexample:
  n = 1
Evaluated terms:
  double n = 2
  n * n = 1
```

::: figure id=fig-01-5 image=jedit-counterexample.png alt="光标位于 lemma double n = n * n 这一行。Output 面板显示：Auto Quickcheck found a counterexample: n = 1。Evaluated terms: double n = 2，n * n = 1。"
Isabelle/jEdit 会对每条新引理运行 Quickcheck。它报告 `n = 1`：`double 1` 是 2，而 `1 * 1` 是 1。
:::

请注意，这个断言在 `n = 0` 和 `n = 2` 时都成立。只试了这两个值的测试者会以为没有问题。Quickcheck 系统地尝试较小的值，所以它找到了 `n = 1`。

这条引理是错的，任何证明都不可能成功。用 `oops` 结束它，`oops` 的意思是放弃一个证明：

```isabelle
  oops
```

如果你还是试了 `by simp` 会怎样？证明会失败，Isabelle 会显示它没能证明的东西：

```isabelle fails
lemma "double n = n * n"
  by simp
```

```output
*** Failed to finish proof⌂:
*** goal (1 subgoal):
***  1. n + n = n * n
```

化简器展开了 `double`，但 `n + n = n * n` 一般并不成立，所以它停了下来。Isabelle/jEdit 用三种方式显示这次失败：边栏里的红色 **!**、`by simp` 下面的红色下划线，以及 Output 面板中的消息“Failed to finish proof”（未能完成证明）（图 1.6）。消息中的 ⌂ 代表这条消息所涉及的位置；在 Isabelle/jEdit 中，它是一个指回文本中那个位置的链接。把 `by simp` 换成 `oops`，错误就消失了。

::: figure id=fig-01-6 image=jedit-error.png alt="lemma double n = n * n 下面的 by simp 这一行背景为红色，边栏里有红色错误图标。Output 面板在红色背景上显示：Failed to finish proof，goal (1 subgoal)，1. n + n = n * n。"
一次失败的证明。错误附在失败的命令上，并显示剩下的目标。它上面那行 `theorem double ?n = ?n * ?n` 并不表示证明成功了：Isabelle/jEdit 并行地检查证明，在证明完成之前就先记下了陈述。红色的消息才是关键。
:::

::: keyidea
现在你已经见到了在整个系列中你会在 Isabelle 里做的三件事：用 `value` **计算**，用 `lemma … by …` **证明**，用 Quickcheck **反驳**。三者之中，只有证明覆盖了每一种情况，也只有证明经过内核的检查。
:::

用 **File → Save**（文件 → 保存）保存这个理论（<kbd>Ctrl</kbd>+<kbd>S</kbd>，macOS 上是 <kbd>Cmd</kbd>+<kbd>S</kbd>）。

## 小结 {#summary}

- 测试只是对输入抽样；它能表明错误存在，却永远不能表明错误不存在。形式化方法用数学描述系统，并检查关于系统**所有**行为的断言。
- 形式化方法包括**形式语言**、**语义**和**证明系统**。
- **规约**说明系统必须做什么。**验证**表明实现满足规约；**确认**检查规约是否正是想要的东西。
- 测试、模型检测、SAT 与 SMT 求解以及交互式定理证明在表达力和自动化之间各有取舍；Isabelle 把定理证明器和自动化工具结合在一起。
- 在 Isabelle 这样的 **LCF 风格**证明器中，只有一个小小的**内核**能创建定理，所以证明工具中的错误不会产生错误的定理。
- Isabelle 的**理论** `T` 放在文件 `T.thy` 中，导入 `Main`，命令写在 `begin` 和 `end` 之间。`value` 用来计算，`lemma … by simp` 用来证明，`quickcheck` 搜索反例，`oops` 放弃一个证明。

## 练习 {#exercises}

:::: exercise 验证还是确认？ {#ex-1-1} ★
对下面每项活动，说明它是验证还是确认，并说明理由。

1. 向客户展示一个列车时刻表系统的规约对下周的列车意味着什么，并问“这是你的意思吗？”。
2. 在 Isabelle 中证明一个排序函数总是返回一个元素相同、并且有序的列表。
3. 发现“对成绩排序”本应写成“最高分排在最前面”。
4. 运行模型检测器，表明一个协议设计的任何可达状态都不违反它的安全性质。

::: solution
1. **确认**：它检查规约描述的是否是客户想要的东西。
2. **验证**：它表明实现满足它的规约。
3. **确认**：它修正的是规约本身。
4. **验证**：它表明一个设计满足一条给定的性质。（设计是对照性质检查的，而性质本身没有对照任何东西检查。这条性质是否正确，是一个确认问题。）
:::
::::

:::: exercise 选哪种方法？ {#ex-1-2} ★
对于下面每项任务，第 1.3 节表格中的哪种方法最合适？

1. 检查一个 32 位乘法器电路在每一对输入上都与参考设计一致。
2. 表明一个三处理器的缓存协议永远不会让两个处理器同时写同一个地址。
3. 证明一个排序函数对任意长度的列表都正确。
4. 给一个解析器输入成千上万个随机输入，快速找出错误。

::: solution
1. **SAT 或 SMT 求解。** 这个问题涉及固定大小的位向量，求解器可以自动处理（这叫做等价性检查）。
2. **模型检测。** 只有三个处理器时，协议的状态是有限的，而性质必须在每个可达状态中成立。
3. **交互式定理证明。** “任意长度”意味着无穷多种情况；这需要归纳，模块 5 和第三部分会讲授。
4. **测试**，具体说是基于性质的测试或随机测试。它不能证明解析器正确，但成本低，能找出很多错误。
:::

:::: exercise 测试要花多长时间？ {#ex-1-3} ★
一个函数接受三个 32 位整数。它有多少种不同的输入？如果每秒测试 $10^9$ 个，全部测完需要多长时间？取一年约为 $3.15 \times 10^7$ 秒。

::: solution
共有 $2^{32} \cdot 2^{32} \cdot 2^{32} = 2^{96} \approx 7.9 \times 10^{28}$ 种输入。每秒测试 $10^9$ 个，需要约 $7.9 \times 10^{19}$ 秒，即 $7.9 \times 10^{19} / (3.15 \times 10^7) \approx 2.5 \times 10^{12}$ 年，大约 2.5 万亿年。
:::

:::: exercise 三倍 {#ex-1-4} ★★
在你的理论中加入一个函数 `triple :: "nat ⇒ nat"`，满足 `triple n = n + n + n`。用 `value` 计算 `triple 14`。然后用 `by simp` 证明两条引理：`triple n = 3 * n` 和 `triple n = double n + n`。

::: solution

```isabelle
fun triple :: "nat ⇒ nat" where

```

```output
"42"
  :: "nat"
```

```isabelle
lemma "triple n = 3 * n"

  by simp
```

两个证明都能成功，因为 `simp` 会展开 `triple` 和 `double` 的定义，然后完成算术运算。

:::: exercise 一条错误的列表定律 {#ex-1-5} ★★
在 Isabelle 中，`xs @ ys` 把两个列表连接起来：`[1, 2] @ [3]` 是 `[1, 2, 3]`。有人断言 `rev (xs @ ys) = rev xs @ rev ys`。用 `quickcheck` 检验这个断言。读懂反例，推出正确的定律应该是什么，并用 `by simp` 证明它。

::: solution
```isabelle
lemma "rev (xs @ ys) = rev xs @ rev ys"
  quickcheck
  oops
```

```output result
Testing conjecture with Quickcheck-exhaustive...

Quickcheck found a counterexample:
  xs = [a⇩2]
  ys = [a⇩1]
Evaluated terms:
  rev (xs @ ys) = [a⇩1, a⇩2]
  rev xs @ rev ys = [a⇩2, a⇩1]
```

当每个列表各有一个元素时，`rev (xs @ ys)` 把 `ys` 的元素放在前面，而 `rev xs @ rev ys` 保持原来的顺序。反转一个连接起来的列表时，各部分的顺序也要反过来：

```isabelle
lemma "rev (xs @ ys) = rev ys @ rev xs"
  by simp
```

Quickcheck 把这两个元素叫做 a₁ 和 a₂：它们是某个未知元素类型中的两个不同的值。
:::
::::

:::: exercise 还有什么需要信任？ {#ex-1-6} ★★★
Isabelle 接受了你的证明：某个 C 函数满足它的规约。请列出至少四种在真实计算机上运行时仍可能导致这个函数行为异常的情况。

::: solution
下面任何一种都有可能，此外还有其他情况：

1. **规约**错误或不完整：它没有说出真正想要的东西（确认失败）。
2. 证明中使用的 **C 语言模型**与 C 标准或编译器的实际行为不同，例如在整数溢出或内存布局方面。
3. **编译器**有错误，生成的机器码与 C 代码不一致（除非编译器也经过了验证，像 CompCert 那样）。
4. **硬件**有故障，或者行为与其文档不同。
5. 定理的**假设**在实际中不成立，例如假设调用者传入的是有效指针，或者假设没有其他线程修改数据。
6. 证明助手的**内核**或逻辑本身是不可靠的。这是可能性最小的一项：内核很小，而且几十年来一直受到仔细审查。
:::
::::

:::: exercise 一个有错误的化简器 {#ex-1-7} ★★★
假设一位程序员在 Isabelle 的化简器中（内核之外）引入了一个错误，使它在每个目标中都把 `0` 重写成 `1`。请解释，当你随后试图用 `simp` 证明错误的陈述 `0 = 1` 时会发生什么，以及 LCF 架构在这里为什么重要。

::: solution
在 LCF 风格的证明器中，化简器不能简单地宣布一个定理：要产生定理，它必须通过应用内核的推理规则来构造，因为只有内核能创建 `thm` 类型的值。内核会检查每一步。把 `0` 重写成 `1` 不是一个合法的步骤：没有任何规则允许它，因为等式 `0 = 1` 不是定理。所以这个有错误的化简器要么失败，要么在试图执行非法步骤时报错，Isabelle 不会接受 `0 = 1`。

因此，这个错误让你失去的是一个能正常工作的化简器，而不是结果的可靠性。在没有这种架构的证明器中，如果化简器可以直接创建定理，同样的错误就会让一个错误的陈述变成定理，而建立在它之上的每一个证明都将毫无价值。
:::
::::

## 自测题 {#quiz}

```quiz
? 一个函数已经对照它的规约经过了形式化验证。这能保证什么？
- [ ] 这个函数没有任何种类的错误
- [x] 只要可信基正确，它对每个输入都满足规约
- [ ] 它能通过客户将来编写的所有测试
```
