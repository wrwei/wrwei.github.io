## 两个元模型与一种映射 {#s1}

组件模型描述端口与接线。普通图模型只需要节点和有向边。**模型到模型转换**（model-to-model transformation）在这两门语言之间翻译：源模型符合组件元模型，目标模型符合另一份图元模型。转换要决定保留什么、省略什么，以及怎样重新建立引用。

这里，每个 `Architecture` 转成 `Graph`，每个 `Component` 转成 `Node`，每个 `Connector` 转成 `Edge`。最简单的版本会丢掉端口名称。这是有意的：图算法可以在组件层面工作，不必知道组件语言中的端口细节。**ETL**（Epsilon Transformation Language）用规则定义这种映射。规则体沿用第 4 模块的 EOL 表达式。

## 编写 ETL 规则 {#s2}

第一个程序有三条规则。`Architecture2Graph` 创建根元素并填充其包含的节点与边；`Component2Node` 复制组件名称；`Connector2Edge` 把边接到源端口和目标端口所属组件对应的图节点上。

{{EXAMPLE:m07-basic}}

阅读实际输出中的目标树：它有名为 `Alarm` 的图、三个节点与两条边。ETL 程序下方可见目标元模型。`Source!Component` 与 `Target!Node` 分别指定不同模型中的类型，避免把源组件误当成目标节点。`g.nodes ::= a.components` 使用 ETL 的特殊赋值：填入每个源组件**经转换后的对应元素**，而非源组件本身。

转换不只是导出文本。它创建另一种语言的模型，可以继续用于其他模型管理任务。本地运行器打印目标模型的包含树供你检查；本课程不把目标持久化为 XMI 文件。

## 解析转换后的对应元素 {#s3}

ETL 保留一份**转换轨迹**（transformation trace），记录源元素及其产出的目标元素。`equivalent()` 取得某源元素经转换后的对应元素。下一个程序与第一个做相同映射，但在填充目标图和连接边的端点时，显式调用 `equivalent()`。

{{EXAMPLE:m07-equivalent}}

比较两次输出：目标图完全一样。`::=` 是目标特性接收对应目标元素时的简便写法。较复杂的表达式需要计算、筛选或组合对应元素时，显式 `equivalent()` 更合适。两种写法都不是按名称猜测对应关系；轨迹记录了哪条规则创建了什么结果。

## 守卫条件与惰性规则 {#s4}

**守卫条件**（guard）限制规则转换哪些源元素。下一个源模型的第二条连接把数字输出接到模拟输入。带守卫条件的连接器规则只在两端端口类型相同的情况下生成边。三个组件仍都生成节点，但只有兼容的连接生成边。

{{EXAMPLE:m07-guard}}

这是一项策略选择，不能代替验证。默默丢弃无效连接，对下游任务可能有危险。项目可以先用 EVL 拒绝模型；也可以明确地只转换有效连接，同时报告被省略的连接。这个示例单独展示守卫条件的效果。

**惰性规则**（lazy rule）只有在请求对应元素时才运行。下一个示例不把组件、而把端口映射成图节点。`Architecture2Graph` 为每个端口请求 `Port2Node`。由于 `Port` 是抽象类、实例实际属于 `InPort` 或 `OutPort`，规则需要 `@greedy`，以匹配子类而非仅匹配完全相同的类型。

{{EXAMPLE:m07-lazy}}

结果有七个节点，标签同时包含所属组件名与端口名。若没有 `@greedy`，在 Epsilon 2.8.0 中这条规则不适用于具体的端口子类，请求到的对应元素便会缺失。`@lazy` 避免在没有规则请求时创建端口节点。它适合有条件或代价较高的结果，不应被用来隐藏本应总是存在的结果。

## 主规则与转换轨迹 {#s5}

有时不止一条规则转换同一种源类型。下一个示例中，`Component2Node` 创建普通节点，`Component2Audit` 创建另一个审计节点。`@primary` 让普通节点在 `equivalent()` 选取单个对应元素时排在第一位。

{{EXAMPLE:m07-primary}}

图包含三个普通节点。非惰性的审计规则也照常运行；因为没有图包含审计节点，本地目标打印器将它们显示为独立根元素。**主规则不会禁止其他规则。**它只控制单元素 `equivalent()` 查询时，哪个对应元素排在前面。如果目标模型只应有图中节点，就要删除审计规则，或有意为审计结果安排容器。[ETL 参考文档](https://eclipse.dev/epsilon/doc/etl/)详细说明规则调度、`equivalent()` 和 `equivalents()`。

## 检查目标模型 {#s6}

转换即便运行成功，也可能丢掉需要的信息。基本图省略端口名称和信号类型；带守卫条件的图省略一条不兼容的连接；主规则示例则有额外的、未被包含的审计节点。把目标元模型和实际输出的目标树放在一起看，才能知道转换后究竟有什么。

对于真实映射，应事先写明预期不变量：节点数、哪些连接器成为边、名称是否保持唯一，以及每条边的端点是否都属于目标图。如果映射依赖正确接线，应先验证源模型；完成转换后也要检查或验证目标模型。第 10 模块会把这套做法用于另一领域。

:::

::: solution
`Architecture` 变成 `Graph`，`Component` 变成 `Node`，`Connector` 变成 `Edge`。基本目标模型省略端口、端口名称和信号类型，只保留组件名称及组件级连接。
:::

::: exercise #e2 level=1 kind=conceptual minutes=5
**理解 `::=`。** 为什么 `g.nodes ::= a.components` 有意义，而把 `a.components` 直接赋给目标的 `Node` 包含引用是错误的？
:::

::: solution
右侧是源模型中的 `Component` 元素。ETL 的 `::=` 解析出它们转换后的 `Node` 对应元素，再填入 `g.nodes`。直接赋值会混用不兼容元模型中的元素。
:::

::: exercise #e3 level=1 kind=conceptual minutes=5
**理解主规则。** 在主规则示例中，图的 `nodes` 只有普通节点，为什么实际输出仍打印了审计节点？

```quiz
? ETL 转换产出什么？
- [ ] 只有格式化文本
- [x] 符合另一个元模型的目标模型
- [ ] 新 Git 分支
- [ ] 只有警告
> ETL 把元素与关系映射到目标模型。

? `Source!Component` 指什么？
- [x] 源模型中的 `Component` 类型
- [ ] EGL 生成的 Java 类
- [ ] 目标图节点
- [ ] Flexmi 文件名
> 带模型限定的类型区分源语言与目标语言。

? 这里的 ETL `::=` 做什么？
- [ ] 把源元素直接赋给目标。
- [x] 赋入转换后的对应元素。
- [ ] 删除源模型。
- [ ] 排序目标节点。
> 特殊赋值经转换轨迹解析对应元素。

? `Connector2Edge` 的守卫条件控制什么？
- [ ] 源元模型能否解析
- [x] 哪些连接器会由这条规则转换
- [ ] 所有节点的名称
- [ ] 是否每条规则都惰性运行
> 守卫条件为假时，这条规则跳过相应源元素。

? 惰性的 `Port2Node` 规则为什么使用 `@greedy`？
- [ ] 为每个节点创建额外副本
- [ ] 更快地写文件
- [x] 通过抽象父类 `Port` 匹配 `InPort` 和 `OutPort` 实例
- [ ] 禁止架构规则
> 如果只匹配完全相同的类型，就会漏掉具体子类。

? 示例中的 `@primary` 保证什么？
- [ ] 没有其他规则转换组件。
- [x] 选取单个对应元素时，普通节点排在第一位。
- [ ] 审计节点被删除。
- [ ] 每条边都兼容。
> 主规则影响对应元素的顺序，不决定其他规则是否执行。

? 转换后应该检查什么？
- [ ] 只检查程序没有解析错误。
- [x] 目标是否具有预期节点、边和需要保留的信息。
- [ ] 只看源文件名。
- [ ] HTML 渲染器是否运行。
> 运行成功仍可能丢失或错误映射数据。
```
