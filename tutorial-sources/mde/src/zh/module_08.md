## 把大语言模型用作起草助手 {#s1}

大语言模型可以建议元模型、示例模型或 Epsilon 程序。其回答只是**草稿**：文本可能能解析，却表达了错误的领域规则；看似合理的说明也可能与模型不符。用元模型定义结构，用 EVL 表达约束，再用可运行示例检验结果。大语言模型可以提出备选方案，最终应由模型中的证据判断方案是否成立。

本节改编自 Dimitris Kolovos 的 [*Metamodelling with ChatGPT*, Episode 2](https://www-users.york.ac.uk/~dk135/blog/metamodelling-with-chatgpt/episode-2/)。该实验发现，提供 Emfatic 示例有助于语言模型给出语法可用的草稿；后续反馈也改进了生成的 EGL 模板。下文的草稿是**专为本教程编写的示例**，不是该实验的原始输出，也不是实时生成的回答。示例不会调用大语言模型服务。

## 审查元模型草稿 {#s2}

第一个示例草稿把 `Connector.source` 和 `Connector.target` 都放宽为抽象的 `Port` 类型。因此，输入端口可以充当源，输出端口可以充当目标。EOL 查询成功运行，并打印出一条方向颠倒的连线。能解析、能运行只说明 Epsilon 能处理这些文件，并不证明连线规则正确。

{{EXAMPLE:m08-draft}}

可以要求起草助手列出类、包含关系、重数、端点方向，以及一个有效和一个无效的实例。逐项对照领域需求审查。尤其要检查 `val` 与 `ref`：连线引用组件拥有的端口，而不包含这些端口的副本。

EVL 可以把方向规则变成可执行的检查。下一项检查拒绝方向颠倒的连线，即使宽松的草稿元模型允许它。在 Playground 中，EVL 结果显示为模型图上的注释；下方记录了同一次验证运行的结果。

{{EXAMPLE:m08-check}}

修正后的元模型限定源为 `OutPort`、目标为 `InPort`。修正后的模型也从 `OrGate.open` 指向 `AndGate.open`。同一 EVL 检查现在通过。

{{EXAMPLE:m08-correct}}

两者提供不同的证据：元模型限制引用类型；EVL 则检查一条也适用于宽松草稿的规则。实际项目还应加入第 5 模块介绍的名称唯一性、信号类型兼容性和连线完整性检查。

## 验证生成的断言 {#s4}

起草助手可能声称警报模型有三条连线，实际只有两条。把这条示例性断言写成约束，差异便可观察，而不必依赖文字表述给人的可信感。

{{EXAMPLE:m08-claims}}

将重要断言转换为测试或查询：元素数量、类型、可达性、唯一性及生成文件的内容。让断言与检查相邻。检查通过只支持它所检验的性质，并不证明整个设计正确。

## 从模型生成提示词 {#s5}

流程也可以从模型走向提示词。EGX 为每个组件创建一份审查提示词，EGL 填入实际端口名称。这些是供人或后续工具使用的文本文件；运行示例不会发送这些文件。

{{EXAMPLE:m08-prompt}}

提示词要求审查者不要编造端口，并对照源模型核查回答。如果之后使用大语言模型，应把回答另存为草稿，再运行相应的 Epsilon 检查。不要未经验证就把回答写入可信模型。

## 建立证据循环 {#s6}

从领域需求出发，撰写或请求一份草稿，运行解析器和检查，检查其输出，然后修订草稿。记录输入和准确的检查结果。对于生成的程序，至少在正常、边界和无效模型上运行；对于生成的文本，既要看生成器是否完成，也要检查生成文件。

不同工具检验不同问题：Emfatic 检验元模型语法，Flexmi 加载实例，EVL 检验领域约束，ETL 通过目标模型检验映射，EGL/EGX 展示生成文本。尚未形式化的需求仍须人工审查。

## 练习 {#exercises}

::: exercise #e1 level=1 kind=conceptual minutes=5
**找出缺口。** 为什么第一份草稿中首条连线方向颠倒，却仍能运行？
:::

::: solution
两个端点引用都使用宽泛的 `Port` 类型，因此可以指向任一种具体端口。执行成功不代表满足预期的输出到输入规则。
:::

::: exercise #e2 level=1 kind=conceptual minutes=5
**区分证据。** Emfatic 解析成功证明什么？EVL 方向约束又证明什么？
:::

::: solution
解析成功表明元模型语法可处理。EVL 约束检查已加载模型中每条连线的方向。两者均不能单独证明全部领域需求。
:::

::: exercise #e3 level=1 kind=conceptual minutes=5
**审查断言。** 一段生成的文字声称有三个组件和三条连线。对于修正后的警报模型，哪一部分属实？
:::

::: solution
模型确有 `OrGate`、`AndGate`、`Siren` 三个组件，但只有两条连线。应核对模型中的数量，而不是依赖文字。
:::

## 自测 {#quiz}

```quiz
? 应怎样对待大语言模型建议的元模型？
- [x] 将其视为需要对照需求和示例检查的草稿
- [ ] 将其视为已验证的领域定义
- [ ] 将其视为可执行的 Java
- [ ] 用它取代模型
> 流畅的草稿也可能包含错误的结构或规则。

? 宽泛的 `Port` 端点类型允许什么？
- [ ] 仅允许输出到输入的连线
- [x] 任一端都可以是输入或输出端口
- [ ] 不允许连线
- [ ] 仅允许外部端口
> 两种具体端口类型都继承 `Port`。

? 哪个示例将方向颠倒的连线判为违规？
- [ ] 仅有 EOL 打印结果
- [x] EVL 端点约束
- [ ] EGX 提示词生成器
- [ ] Git 提交
> EVL 检查明确表达了预期方向。

? 修正后的警报模型有几条连线？
- [ ] 一条
- [x] 两条
- [ ] 三条
- [ ] 四条
> 模型中有两个连线元素。

? EGX 示例执行什么任务？
- [x] 从组件生成本地文本提示词
- [ ] 调用在线大语言模型
- [ ] 验证所有可能的输出
- [ ] 修改元模型
> EGX 生成文件，没有调用大语言模型。

? 后续收到大语言模型回答后应该做什么？
- [ ] 文字流畅就相信它。
- [x] 将其保存为草稿，检查其断言或产物。
- [ ] 删除原始模型。
- [ ] 略过无效情况。
> 应对回答重复证据循环。

? 一项约束通过能证明什么？
- [ ] 整个系统正确。
- [x] 本次运行和模型满足被检查的性质。
- [ ] 大语言模型曾用该模型训练。
- [ ] 所有生成代码均可编译。
> 检查的范围是明确且有限的。
```
