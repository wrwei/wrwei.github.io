Programs in a logic

In Part II you used Isabelle to check proofs about formulas. Part III turns to the other half of Isabelle/HOL: its executable definitions form a programming language. HOL contains a typed functional programming language, close to Haskell, OCaml and Standard ML (the language of Isabelle’s own core). You write programs as equations, Isabelle runs them, and because the programs are part of the logic, you can prove facts about them. Modules 9 to 11 are about the proving; this module is about the programming.

Programs in HOL differ from programs in Python, Java or C in three ways.

  • No side effects. A HOL function does not change variables, print, or read files. Its arguments determine its mathematical value. State changes can be modelled explicitly by passing a state in and out.
  • Recursion for repetition. The functions here use recursion, as in Module 5. Loops can also be modelled in HOL; they are not a primitive construct in these function definitions.
  • Every function is total. It denotes a value for every argument of its type. This does not mean that every HOL function has executable code, or that every evaluation succeeds. Section 8.7 explains why recursive equations accepted by fun need a termination proof.

This module builds one example step by step: a controller for a British traffic light, which shows red, then red and amber together, then green, then amber, and then red again. You will describe its states as a data type, compute its sequence of states and their timing with lists and numbers, check a safety rule for a junction, and finally generate Haskell code for it. On the way you will meet the errors that beginners meet, with Isabelle’s real messages.

Start a new theory for this module, as in Module 1 (for example Traffic.thy with theory Traffic), and type the blocks into it as you read.

Types

Every term in HOL has a type, and Isabelle checks types before it does anything else. Types rule out nonsense such as adding a number to a list: a term that cannot be given a type is rejected at once.

Type Its values Examples
bool the truth values True, False
nat the natural numbers 0, 1, 2, … 0, Suc 0, 42
int the integers …, −1, 0, 1, … -3, 7
'a list finite lists of elements of type 'a [], [1, 2, 3]
'a × 'b pairs of an 'a and a 'b (3, True)
'a option no value, or one value of type 'a None, Some 5
'a ⇒ 'b functions from 'a to 'b Suc, rev
Definition 8.1Types in HOL

A base type such as bool, nat or int is a name. A type constructor such as list or option builds a type from other types and is written after its arguments: nat list is the type of lists of natural numbers, and nat list list the type of lists of such lists. 'a × 'b is the type of pairs and 'a ⇒ 'b the type of functions. A type variable 'a, 'b, … stands for any type; a function whose type contains one, such as rev :: 'a list ⇒ 'a list, works for every instance of it and is called polymorphic.

Read t :: τ as “t has type τ”. Type the function arrow ⇒ as => and the product sign × as <*> (or write * instead of ×). The arrow binds more weakly than any type constructor, so nat ⇒ bool list means nat ⇒ (bool list).

The command typ checks that a type is well formed and prints it back:

Isabelle
typ "nat × bool"
typ "nat ⇒ bool list"
typ "(nat ⇒ bool) list"
Output
"nat × bool"

"nat ⇒ bool list"

"(nat ⇒ bool) list"

Isabelle prints each type with as few parentheses as possible. The second type needs none, because ⇒ binds most weakly; the third needs them, because it is a list of functions, not a function that returns a list.

Terms and type inference

A term is an expression of HOL: a constant such as True, 0 or rev, a variable such as x, a function applied to arguments such as rev xs, or one of the forms this module introduces. The command term reads a term, works out its type and prints both, without running it as a program:

Isabelle
term "Suc 0"
term "[Suc 0, 5]"
term "(Suc 0, [True])"
Output
"Suc 0"
  :: "nat"

"[Suc 0, 5]"
  :: "nat list"

"(Suc 0, [True])"
  :: "nat × bool list"

You never said that 5 is a natural number; Isabelle worked it out. All elements of a list have one type, Suc 0 is a nat, so 5 must be a nat too. In the last term, the pair has a nat on the left and a bool list on the right, so its type is nat × bool list.

Definition 8.2Type inference and type annotations

Type inference computes the type of every part of a term from the types of its constants and variables and the constraints imposed by application and binding. Where the constants leave the type open, the result contains type variables. A type annotation t :: τ (or (t::τ) inside a larger term) tells Isabelle that t has type τ.

Here the constants leave the type open:

Isabelle
term "x + 1"
Output
"x + 1"
  :: "'a"

The variable x and the number 1 could be natural numbers, integers or real numbers: all of them have + and 1. Isabelle answers with the type variable 'a, “some type”. One annotation settles it:

Isabelle
term "x + (1::nat)"
Output
"x + 1"
  :: "nat"

Since + takes two arguments of the same type, x is now a nat too. Section 8.6 explains what Isabelle knows about the 'a in x + 1.

x is a free variable: it is neither a declared constant nor bound by a quantifier or λ. Isabelle/jEdit shows free variables in blue, and constants such as Suc in black.

Computing with value

value evaluates a term and prints the result with its type, as in Module 1. It also works with free variables, which it treats as unknown values:

Isabelle
value "rev [a, b, c]"
Output
"[c, b, a]"
  :: "'a list"

Isabelle reversed a list of three elements it knows nothing about. This is useful for testing a function on symbolic inputs.

Watch out

A misspelt name is a free variable too. Isabelle has no constant lenght, so here it takes lenght to be an unknown function and hands the term back unevaluated, with an unknown type:

Isabelle
value "lenght [1, 2::nat]"
Output
"lenght [1, 2]"
  :: "'a"

There is no error message. When value returns your term unchanged with a type variable such as 'a, look for a misspelt name: Isabelle/jEdit shows it in blue, like any variable.

When types do not fit

A term that cannot be typed is rejected with a message. Suc takes a natural number, and True is not one:

Isabellefails on purpose
value "Suc True"
Output
Type unification failed: Clash of types "bool" and "nat"

Type error in application: incompatible operand type

Operator:  Suc :: nat ⇒ nat
Operand:   True :: bool

Read the message from the top:

  • Type unification failed. To type an application f a, Isabelle must make the argument type of f equal to the type of a. Finding types that make two types equal is called type unification: the same idea as the unification of formulas in Module 7, applied to types. Here it failed.
  • Clash of types “bool” and “nat” names the two types that could not be made equal.
  • Operator is the function, Suc :: nat ⇒ nat; Operand is the argument, True :: bool.

Giving a function too many arguments produces a different message. rev takes one list:

Isabellefails on purpose
value "rev [1, 2::nat] [3]"
Output
Type unification failed: Clash of types "_ ⇒ _" and "_ list"

Type error in application: operator not of function type

Operator:  rev [1, 2] :: nat list
Operand:   [3::??'a] :: ??'a list

Isabelle reads rev [1, 2] [3] as the list rev [1, 2] applied to [3]. A list is not a function, so the operator rev [1, 2] is “not of function type”. In the clash, _ ⇒ _ stands for “some function type” and _ list for “some list type”. The type ??'a of [3] is a type variable that Isabelle invented while it worked on the term and never had to fix.

Functions are values

In HOL a function is a value like a number or a list. You can pass it to another function, return it as a result, and keep it in a list. This section shows how to write functions without naming them, and how functions of several arguments work.

λ-abstraction

To write a function without giving it a name, use λ-abstraction: λx. x + 1 is the function that maps x to x + 1. Read it “lambda x, x plus 1”. Type λ as % or \lambda.

Definition 8.3λ-abstraction and application

If t is a term of type τ₂ in which the variable x of type τ₁ may occur, then λx. t is the function of type τ₁ ⇒ τ₂ that maps each value x to t. Application of a function f to an argument a is written f a, without parentheses or commas. Applying λx. t to a replaces the free occurrences of x in t by a, renaming bound variables when needed to avoid capturing variables of a (Module 3). This step is called β-reduction.

Isabelle
term "λx::nat. x + 1"
Output
"λx. x + 1"
  :: "nat ⇒ nat"

The annotation x::nat after the λ fixes the type of the bound variable, so the function has type nat ⇒ nat. Now apply a function to an argument:

Isabelle
value "(λx::nat. x * x) 7"
Output
"49"
  :: "nat"

The difference between term and value shows here too. term shows the term after the β-reduction step, but it does no arithmetic:

Isabelle
term "(λx::nat. x * x) 7"
Output
"7 * 7"
  :: "nat"

Functions of several arguments

Every HOL function takes exactly one argument. A function of two numbers takes the first number and returns a function that waits for the second. Its type is nat ⇒ nat ⇒ nat, which means nat ⇒ (nat ⇒ nat), because ⇒ groups to the right. Application groups to the left: f x y means (f x) y. Figure 8.1 follows the two steps.

Definition 8.4Currying and partial application

Writing a function of several arguments as a function that takes the first argument and returns a function of the rest is called currying, after the logician Haskell Curry. Applying such a function to fewer arguments than it can take is partial application; the result is a function.

The infix + is notation for a curried function whose name is (+): x + y is short for (+) x y. You can see this when you write a function of two arguments with a λ:

Isabelle
term "λx y. x + (y::nat)"
Output
"(+)"
  :: "nat ⇒ nat ⇒ nat"

Isabelle prints (+) instead of your λ-term. The two are the same function: λx y. x + y takes x and y and adds them, which is exactly what (+) does, and Isabelle prints the shorter form. A partial application of (+) is a function of one argument:

Isabelle
term "(+) (3::nat)"
Output
"(+) 3"
  :: "nat ⇒ nat"

Functions that take functions as arguments are called higher-order. The most common one is map, which applies a function to every element of a list:

Isabelle
term "map"
Output
"map"
  :: "('a ⇒ 'b) ⇒ 'a list ⇒ 'b list"

The type says it all: map takes a function from 'a to 'b and a list of 'as, and returns a list of 'bs. Give it the partial application from above:

Isabelle
value "map ((+) (3::nat)) [1, 2, 3]"
Output
"[4, 5, 6]"
  :: "nat list"

HOL is called higher-order logic for the same reason: its variables, too, may stand for functions, and its quantifiers may range over them.

Good to know

You could also write a function of two numbers as a function on pairs, of type nat × nat ⇒ nat. It takes one argument, a pair. Isabelle’s library almost always uses the curried form instead, because it allows partial application, as in map ((+) 3).

Watch out

Application groups to the left, so Suc Suc 0 means (Suc Suc) 0: Suc applied to the function Suc.

Isabellefails on purpose
value "Suc Suc 0"
Output
Type unification failed: Clash of types "_ ⇒ _" and "nat"

Type error in application: incompatible operand type

Operator:  Suc :: nat ⇒ nat
Operand:   Suc :: nat ⇒ nat

The operand of Suc is the function Suc :: nat ⇒ nat where a nat is needed. Write Suc (Suc 0). Missing parentheses are a common cause of type errors.

Data types

Now the traffic light. At any moment it is in one of four states. HOL lets you define a new type whose values are exactly these states.

Enumerations

Isabelle
datatype light = Red | RedAmber | Green | Amber

This command introduces the type light and four constructors, Red, RedAmber, Green and Amber, the values of the type. Constructor names start with a capital letter by convention.

Isabelle
term "Green"
Output
"Green"
  :: "light"
Definition 8.5Datatype

A declaration datatype t = C₁ τ… | … | Cₙ τ… introduces a new type t whose values are built with the constructors C₁, …, Cₙ. Each constructor takes arguments of the types listed after it (possibly none). Values built with different constructors are different; values built with the same constructor are equal only if their arguments are equal; and every value of t is built with the constructors. A datatype whose constructors take no arguments is an enumeration.

A function on light says what to do for each constructor. The traffic light’s next state:

Isabelle
fun next_light :: "light ⇒ light" where
  "next_light Red = RedAmber"
| "next_light RedAmber = Green"
| "next_light Green = Amber"
| "next_light Amber = Red"
Output
consts
  next_light :: "light ⇒ light"

Found termination order: "{}"

This is pattern matching: the left-hand side of each equation contains a pattern, here a constructor, that says which arguments the equation is for. The equations are separated by |. Isabelle reports the new constant with its type, and a termination order, "{}", which is empty because next_light does not call itself; Section 8.7 explains these reports.

Isabelle
value "next_light (next_light Red)"
Output
"Green"
  :: "light"

The datatype supplies the constructor properties of Definition 8.5. Distinctness and injectivity are available to simp; exhaustiveness supports the cases method below. simp proves at once that two constructors differ:

Isabelle
lemma "Red ≠ Green"
  by simp

Every light is one of the four constructors, so you can prove a claim about all lights by checking each constructor in turn. The proof method cases l splits a goal into one case per constructor:

Isabelle
lemma "next_light (next_light (next_light (next_light l))) = l"
  apply (cases l)
Output
proof (prove)
goal (4 subgoals):
 1. l = Red ⟹ next_light (next_light (next_light (next_light l))) = l
 2. l = RedAmber ⟹ next_light (next_light (next_light (next_light l))) = l
 3. l = Green ⟹ next_light (next_light (next_light (next_light l))) = l
 4. l = Amber ⟹ next_light (next_light (next_light (next_light l))) = l

Each subgoal assumes a different value for l. simp uses the assumption to replace l and then computes:

Isabelle
  apply simp_all
  done

simp_all applies simp to all subgoals. Evaluating the equation at one light would check that instance; the lemma covers all four. Since this type is finite, an exhaustive computation could also check all four.

Finally, the light’s timing. Each state lasts a fixed number of seconds:

Isabelle
fun duration :: "light ⇒ nat" where
  "duration Red = 30"
| "duration RedAmber = 2"
| "duration Green = 25"
| "duration Amber = 3"

Recursive data types

A list can be arbitrarily long, so no enumeration can describe all lists. A recursive datatype refers to itself in its definition. Here is a stack, the last-in, first-out store found in every programming course, as a datatype of your own:

Isabelle
datatype 'a stack = Empty | Push 'a "'a stack"

Read it as: a stack of elements of type 'a is either Empty, or Push x s, an element x pushed on top of a stack s. The type variable makes the type polymorphic: nat stack, light stack and so on. An argument type that is more than a single name, such as 'a stack, goes in quotation marks.

Isabelle
term "Push (1::nat) (Push 2 (Push 3 Empty))"
Output
"Push 1 (Push 2 (Push 3 Empty))"
  :: "nat stack"

Figure 8.2 draws this value as a tree. Each Push has two branches, the element and the rest of the stack, and the tree ends in Empty.

Isabelle’s own lists are a datatype of exactly this shape. The library theory List defines them, in essence, as datatype 'a list = Nil | Cons 'a "'a list", with the notation [] for Nil and the infix x # xs for Cons x xs. The list [1, 2, 3] is notation for 1 # 2 # 3 # [], where # groups to the right. Every list you have used so far was built with these two constructors.

Functions on a recursive datatype are usually recursive too. One equation per constructor, with a recursive call on the inner stack:

Isabelle
primrec height :: "'a stack ⇒ nat" where
  "height Empty = 0"
| "height (Push x s) = Suc (height s)"

primrec to_list :: "'a stack ⇒ 'a list" where
  "to_list Empty = []"
| "to_list (Push x s) = x # to_list s"
Output
consts
  height :: "'a stack ⇒ nat"

consts
  to_list :: "'a stack ⇒ 'a list"

primrec is a variant of fun for this simple kind of recursion; Section 8.4 compares them. to_list turns a stack into a list, top element first:

Isabelle
value "to_list (Push (1::nat) (Push 2 (Push 3 Empty)))"
Output
"[1, 2, 3]"
  :: "nat list"

Options and pairs

What is the top element of an empty stack? An implementation might raise an exception; an invalid memory access in C can have undefined behaviour. A HOL function of type 'a stack ⇒ 'a instead denotes some element even for Empty, without necessarily providing code to compute it. To represent the missing result explicitly, change the result type. HOL’s library defines, in essence,

datatype 'a option = None | Some 'a

A value of type 'a option is either None, “no result”, or Some x, the result x. Functions that can fail return an option:

Isabelle
fun top :: "'a stack ⇒ 'a option" where
  "top Empty = None"
| "top (Push x s) = Some x"

fun pop :: "'a stack ⇒ ('a × 'a stack) option" where
  "pop Empty = None"
| "pop (Push x s) = Some (x, s)"

pop returns two things at once, the top element and the rest of the stack, as a pair (x, s) of type 'a × 'a stack.

Isabelle
value "pop (Push Red (Push Green Empty))"
Output
"Some (Red, Push Green Empty)"
  :: "(light × light stack) option"
Definition 8.6Pairs and options

A pair (a, b) has type τ₁ × τ₂ when a :: τ₁ and b :: τ₂; the functions fst and snd return its first and second component. A triple (a, b, c) is short for (a, (b, c)). The option type 'a option has the values None and Some x for every x :: 'a; it is the type of results that may be missing.

Taking values apart with case

A function that receives an option must deal with both possibilities. Besides pattern matching in equations, HOL has a case expression that matches a value against patterns inside a term:

Isabelle
fun top_or :: "'a ⇒ 'a stack ⇒ 'a" where
  "top_or d s = (case top s of None ⇒ d | Some x ⇒ x)"

top_or d s is the top element of s, or the default d if s is empty. Read case t of p₁ ⇒ e₁ | p₂ ⇒ e₂ as: compute t, find the first pattern pᵢ that matches its value, and return eᵢ, with the variables of the pattern standing for the matching parts. The arrow is the same ⇒ as in function types. A case expression inside a larger term often needs parentheses to mark its extent, like if … then … else ….

Isabelle
value "top_or Red (Push Green Empty)"
value "top_or Red Empty"
Output
"Green"
  :: "light"

"Red"
  :: "light"

Patterns can be nested. Some (x, s) matches an option that contains a pair, and names both parts:

Isabelle
value "case pop (Push Green (Push Red Empty)) of None ⇒ [] | Some (x, s) ⇒ [x, x]"
Output
"[Green, Green]"
  :: "light list"
Tip

fun equations and case expressions are two ways to write the same thing. Use equations when a function’s behaviour depends on the shape of its arguments; use case when one intermediate result, such as top s above, has to be taken apart.

Three ways to define a function

You have now used fun and primrec. HOL has a third command, definition. The three differ in what they accept, in what they prove for you, and in how proofs use them.

Non-recursive functions: definition

The traffic light stands at a crossroads, where two lights control the two directions, north–south and east–west. A simple, strict safety rule says that at every moment at least one of the two lights is in the state Red (red alone, not red and amber). The state of the junction is a pair of lights, and the rule is a function on such pairs:

Isabelle
definition safe :: "light × light ⇒ bool" where
  "safe p = (fst p = Red ∨ snd p = Red)"
Output
consts
  safe :: "light × light ⇒ bool"

definition introduces a constant with a single equation f x₁ … xₙ = t, where the right-hand side t must not mention f: no recursion and no pattern matching. Isabelle stores the equation as a theorem named safe_def:

Isabelle
thm safe_def
Output
safe ?p = (fst ?p = Red ∨ snd ?p = Red)

The question marks are the schematic variables of Module 7: the equation holds for every p. Now prove that one particular state is safe:

Isabellefails on purpose
lemma "safe (Red, Green)"
  by simp
Output
Failed to apply initial proof method⌂:
goal (1 subgoal):
 1. safe (Red, Green)

simp could not even start. Unlike the equations of fun and primrec, the equation of a definition is not given to the simplifier, so for simp, safe is an unknown function. Name the definition and simp uses it:

Isabelle
lemma "safe (Red, Green)"
  by (simp add: safe_def)

lemma "¬ safe (Green, Amber)"
  by (simp add: safe_def)

lemma safe_Red: "safe (Red, l)"
  by (simp add: safe_def)

The last lemma holds for every state l of the east–west light: whatever it shows, the junction is safe while the north–south light is red.

Key idea

By default, definition does not register its equation as a simplification rule. You can supply it with simp add: f_def or register it for later use (Module 9). This is deliberate. A definition introduces a concept; once you have proved its important properties, such as safe_Red, later proofs should use those properties rather than the definition. Proofs then stay short, and if the definition changes, only the proofs of the properties need repair. Module 9 shows more ways of controlling the simplifier.

Watch out

definition takes no patterns. A pattern for the pair on the left-hand side is rejected:

Isabellefails on purpose
definition safe2 :: "light × light ⇒ bool" where
  "safe2 (a, b) = (a = Red ∨ b = Red)"
Output
Bad arguments on lhs: "(a, b)"
The error(s) above occurred in definition:
"safe2 (a, b) ≡
 a = Red ∨
 b =
 Red"

Use fst and snd as above, a case expression, or fun, which accepts patterns.

Recursive functions: fun and primrec

For the simple datatypes here, primrec uses primitive recursion: constructor patterns with variables for the constructor arguments, and recursive calls only on the immediate recursive parts of the argument, such as height s in the equation for Push x s. Such a function always terminates, so primrec needs no termination proof; it reports only the new constant, as you saw for height.

fun accepts much more: nested patterns, patterns on several arguments, equations that overlap, and a broad range of recursive definitions whose termination Isabelle proves automatically. This function pushes the elements of a list onto a stack, one after another; its recursive call changes both arguments:

Isabelle
fun push_all :: "'a list ⇒ 'a stack ⇒ 'a stack" where
  "push_all [] s = s"
| "push_all (x # xs) s = push_all xs (Push x s)"
Output
consts
  push_all :: "'a list ⇒ 'a stack ⇒ 'a stack"

Found termination order: "(λp. length (fst p)) <*mlex*> {}"

fun reports how it proved termination: the length of the first argument, fst p of the pair p of arguments, decreases in every recursive call. The element pushed last ends on top:

Isabelle
value "to_list (push_all [1, 2, 3::nat] Empty)"
Output
"[3, 2, 1]"
  :: "nat list"

Both commands give the simplifier the defining equations under the name f.simps:

Isabelle
thm height.simps
Output
  height Empty = 0
  height (Push ?x ?s) = Suc (height ?s)
definition primrec fun
Recursion none primitive: on the immediate parts general, once termination is proved
Patterns none: f x₁ … xₙ = t constructor patterns with variable arguments constructor patterns, also nested and overlapping
Used by simp not registered by default; add f_def f.simps registered by default f.simps registered by default
Termination no question guaranteed by the form proved automatically, or the definition is rejected

Which to choose? Use definition for a non-recursive concept that you want to reason about abstractly, fun for recursive functions and for anything that needs patterns, and primrec when a function follows the structure of a datatype exactly and you want to be sure no termination proof is involved. Many users write fun almost everywhere, as Module 1 did for double.

Missing and overlapping patterns

What if the equations do not cover every constructor? This function forgets the empty stack:

Isabelle
fun top_value :: "'a stack ⇒ 'a" where
  "top_value (Push x s) = x"
Output
Missing patterns in function definition:
top_value Empty = undefined

consts
  top_value :: "'a stack ⇒ 'a"

Found termination order: "{}"

Isabelle accepts the definition with a warning, and completes it with the equation top_value Empty = undefined. It uses this equation to construct the function, but it does not add it to top_value.simps, so simp does not use it automatically. Here undefined is a polymorphic constant whose value is not specified beyond its type: top_value Empty is some element, with no particular element selected by the definition. The function is total, as every HOL function is, but on Empty it is unspecified. When you try to compute that value, the code behind value has no equation to use and stops with an exception (Section 8.8 explains where this code comes from):

Isabellefails on purpose
value "top_value (Empty :: nat stack)"
Output
exception Match raised⌂

The ⌂ points into the generated program, not into your theory. The library’s hd, the first element of a list, is unspecified for [] in the same way, and value "hd ([] :: light list)" fails with the same exception.

Tip

Missing patterns are often a sign of a missing case in your thinking. Prefer an option result, as in top, so that the caller has to handle the empty case. primrec warns about a missing constructor too, with the message No equation for constructor "Empty".

Equations may also overlap: one argument may match several patterns. fun then uses the first equation that matches, as Haskell and ML do:

Isabelle
fun is_red :: "light ⇒ bool" where
  "is_red Red = True"
| "is_red l = False"

The variable l matches every light, Red included. fun resolves the overlap by turning the second equation into one equation for each remaining constructor, as thm shows:

Isabelle
thm is_red.simps
Output
  is_red Red = True
  is_red RedAmber = False
  is_red Green = False
  is_red Amber = False

The order of the equations therefore matters. Put the general equation first, and the specific one can never be used. Isabelle rejects such a definition:

Isabellefails on purpose
fun is_red2 :: "light ⇒ bool" where

List comprehension

Combinations of map and filter can also be written as a list comprehension, as in Haskell and Python. [e. x ← xs, P x] is the list of the values of e for the elements x of xs that satisfy P x. Type ← as <-. Here are the short states of a cycle, with their durations:

Isabelle
value "[(l, duration l). l ← trace 4 Red, duration l < 10]"
Output
"[(RedAmber, 2), (Amber, 3)]"
  :: "(light × nat) list"

The expression (l, duration l) builds a pair for each element; l ← trace 4 Red is a generator, which takes the elements l of the list one by one; duration l < 10 is a condition. There can be several generators and conditions, separated by commas.

Watch out

Some list functions are unspecified for some arguments: hd [], the first element of the empty list, and xs ! n when n is not a position of xs. They denote some value of the right type, without specifying which, and computing it with value stops with an exception, as for top_value in Section 8.4. Before you use hd xs or xs ! n in a definition, make sure that xs is not empty or that n < length xs.

Numbers and type classes

HOL has several types of numbers: nat, int, and, with the theory Complex_Main, real and complex. This series needs only nat and int.

Natural numbers and integers

The type nat behaves like a datatype with two constructors, 0 and Suc: every natural number is either 0 or Suc n for a smaller natural number n. That is why you can define functions on nat by pattern matching on 0 and Suc n, as trace does. A numeral such as 3 denotes the same number as Suc (Suc (Suc 0)) (though the two are written differently, which matters for simp, as the pitfall at the end of this section shows), and value prints natural numbers as numerals:

Isabelle
value "Suc (Suc 0)"
Output
"2"
  :: "nat"

The type int contains the negative numbers too. The two types differ most visibly in subtraction:

Isabelle
value "(2::nat) - 3"
value "(2::int) - 3"
Output
"0"
  :: "nat"

"- 1"
  :: "int"

Isabelle prints negative numbers with a space after the minus sign.

Definition 8.7Truncated subtraction

On nat, subtraction is truncated: m - n is 0 whenever m ≤ n, because there is no natural number below 0. On int, subtraction is the usual one.

Watch out

Truncated subtraction breaks familiar laws. On nat, (m - n) + n = m holds only if n ≤ m: with m = 5 and n = 7, the left side is 0 + 7 = 7. A bank account whose balance is a nat cannot go overdrawn: withdrawing too much leaves exactly 0, silently, instead of a debt. When negative values make sense, use int; when they do not, check n ≤ m before you subtract.

Division on nat and int is div, with remainder mod:

Isabelle
value "(17::nat) div 5"
value "(17::nat) mod 5"
value "(-17::int) div 5"
value "(-17::int) mod 5"
Output
"3"
  :: "nat"

"2"
  :: "nat"

"- 4"
  :: "int"

"3"
  :: "int"

On int, div rounds down, towards minus infinity, so -17 div 5 is −4, and mod is chosen to make (a div b) * b + a mod b = a hold: (−4) · 5 + 3 = −17. And division by zero?

Isabelle
value "(17::nat) div 0"
Output
"0"
  :: "nat"
Fact 8.1Division by zero

In HOL, a div 0 = 0 and a mod 0 = a for every a (the library’s lemmas div_by_0 and mod_by_0).

This is not a mistake. Every HOL function is total, so 17 div 0 must be some number. The library chooses 0, a value that makes many laws hold without side conditions. A program that is required to reject division by zero needs an explicit check; the logic does not raise an error for this operation. When division by zero matters, state b ≠ 0 as an assumption in your lemmas.

The functions int :: nat ⇒ int and nat :: int ⇒ nat convert between the two types; nat maps negative integers to 0. The operator / is division on fields such as the real numbers, not on nat or int, and x ^ n is the power xⁿ, with n a natural number.

Overloading and type classes

You have used +, 0 and numerals on both nat and int. Such names are overloaded: one name has several meanings, chosen by the type. And yet they do not exist for every type. A light is not a number:

Isabellefails on purpose
value "next_light 3"
Output
Type unification failed: No type arity light :: numeral

Type error in application: incompatible operand type

Operator:  next_light :: light ⇒ light
Operand:   3::??'a :: ??'a

“No type arity light :: numeral” says that the type light is not in the class numeral, the class of types that have numerals, so 3 cannot be a light. (An arity is Isabelle’s record that a type belongs to a class.) Isabelle organises overloading in type classes.

Definition 8.8Type class and sort

A type class is a named collection of types that provide certain operations, sometimes with laws. For example, the class plus contains the types that have an operation +, zero those with a 0, numeral those with numerals 1, 2, 3, … and an associative +, and ord those with ≤ and <. A type in a class is an instance of it: nat and int are instances of all four. A sort is a set of classes, written {c₁, …, cₙ}, or c for a single class. A type variable can be restricted to a sort: 'a::{one, plus} stands for any type that is an instance of both one and plus.

Think of it like this

Type classes play the role of interfaces in Java or traits in Rust, and Haskell’s type classes are the same idea. A sort says which interfaces an unknown type must implement.

Watch out

“Sort” has a different meaning here from the one in Module 3. There, in many-sorted logic, a sort was a kind of individual, much what Isabelle calls a type. In Isabelle a sort is a set of type classes: a constraint on a type, not a type.

Isabelle hides sorts unless you ask for them. The option show_sorts makes them visible:

Isabelle
declare [[show_sorts]]
term "x + 1"
term "2 + 2"
declare [[show_sorts = false]]
Output
"(x::'a::{one,plus}) + 1"
  :: "'a::{one,plus}"

"(2::'a::numeral) + (2::'a::numeral)"
  :: "'a::numeral"

Now you can see what Isabelle knows about the 'a of Section 8.1: x + 1 has some type that has 1 and +. And 2 + 2 has some type of the class numeral. That is the key to the message from Module 1, which promised that you would learn to read it here:

Isabellefails on purpose
value "2 + 2"
Output
Wellsortedness error:
Type 'a not of sort term_of
Cannot derive subsort relation numeral < term_of

To print a result, value must turn the computed value back into a term. It does so with an overloaded function term_of, which exists for the types in the class term_of: nat, int, lists, and the datatypes you define, among others. Now read the message line by line.

  • Wellsortedness error: some type is required to be in a class it is not known to be in.
  • Type 'a not of sort term_of: the type of 2 + 2 is the unknown 'a, and value needs it to be in the class term_of.
  • Cannot derive subsort relation numeral < term_of: all Isabelle knows about 'a is that it is in numeral. That would be enough only if every type in numeral were also in term_of, that is, if numeral were a subclass of term_of, written numeral < term_of. It is not.

The cure is the one from Module 1: say which type you mean, as in value "2 + 2 :: nat". The same missing information can make a proof fail:

Isabellefails on purpose

  by simp
Output

goal (1 subgoal):
 1. x + 0 = x

The goal is about a type of sort {plus, zero}: a type with some + and some 0. Nothing in those classes says that 0 is neutral for +, so the claim cannot be proved for every such type. For natural numbers it is a law of arithmetic:

Isabelle

  by simp
Watch out

value computes with numerals, but simp does not match a numeral against a Suc pattern. The equations of trace are about 0 and Suc n, and 2 is neither, syntactically:

Isabelle

  by (simp add: numeral_eq_Suc)

Why fun requires termination

Every fun you have written produced a line “Found termination order”. Module 5 (Section 5.7) explained why Isabelle insists on termination, what a measure is, and how to read the message when fun rejects a definition. Module 1 promised that this module would explain why termination matters, so this section recalls the argument and connects it with the three ways of defining a function in Section 8.4. Then it reads Isabelle’s termination messages in full, and shows what to do when a function terminates but Isabelle cannot see why.

Total functions and consistency

When you define a function with fun, Isabelle makes your equations into theorems: after fun next_light, the equation next_light Red = RedAmber is a theorem you can use in any proof. This is only safe if some function really satisfies the equations. Module 5 showed what goes wrong otherwise, with the “definition” bad n = bad n + 1 of a function bad :: nat ⇒ nat. Suppose Isabelle accepted it:

  1. The equation would be a theorem for every n. Take n = 0 and write k for the number bad 0: the theorem says k = k + 1.
  2. Subtract k from both sides. This works even with truncated subtraction: k - k = 0 and (k + 1) - k = 1. So 0 = 1 would be a theorem.
  3. But 0 ≠ 1 is a theorem too: 1 is Suc 0, and values built with different constructors are different (Definition 8.5; nat behaves like a datatype, Section 8.6).
  4. A statement and its negation together are a contradiction, and from a contradiction every statement follows: the principle of explosion of Module 2, the rule (⊥E) of Module 6.

One bad equation would make every statement a theorem, and every proof would be worthless.

Key idea

A definition as in Section 8.4 is safe without any proof: its right-hand side does not mention the constant being defined, so it cannot be circular, and it can never make the logic inconsistent. fun does not take your recursive equations on trust. It first defines the function by non-recursive definitions of this safe kind, through a construction that Isabelle carries out for you, and then proves your equations from them as theorems. That proof needs a termination argument. If Isabelle cannot find one, fun fails: it does not provide the unrestricted defining equations as theorems. The underlying function package can retain a partial definition and conditional facts, which are beyond this introduction.

If every chain of recursive calls ends in an equation without a recursive call, the equations determine the function’s value for every argument, one step at a time, as in Example 8.1, and the proof goes through. Not every non-terminating equation is contradictory: Module 5 pointed out that every function satisfies f n = f n. But fun does not try to tell harmless equations from harmful ones; it accepts recursion only with a termination proof. A missing pattern (Section 8.4) is a different matter: it leaves a value unspecified, which can never contradict anything, so fun only warns about it.

Reading the termination messages

To prove termination, Isabelle looks for a measure, as in Module 5: a function from the arguments to the natural numbers that becomes smaller with every recursive call. The measures it tries are built from the sizes of the arguments.

Definition 8.9Size

For the datatypes here, Isabelle supplies a size, a natural number written size x. For a natural number n the size is n itself, and for a list its length. For our stack, Empty has size 0 and each Push adds 1 to the size of the inner stack: size (Push 1 (Push 2 Empty)) is 2. Every light has size 0. Other datatypes can have different size equations; inspect their generated t.size facts rather than assuming that size counts every constructor or every stored element.

When the search succeeds, fun prints the measure it found. You have seen three kinds of report in this module:

Report Meaning
"{}" no recursive calls, nothing to prove (next_light, top)
"(λp. size (fst p)) <*mlex*> {}" the size of the first argument decreases (trace)
"(λp. length (fst p)) <*mlex*> {}" the length of the first argument, a list, decreases (push_all)

As in Module 5, the arguments of a function with several arguments form one tuple p, so fst p is the first argument. <*mlex*> chains measures lexicographically, as for Ackermann’s function in Module 5: if the first measure stays the same, the next one must decrease. The final {} ends the chain.

When the search fails, Isabelle prints what it tried. Module 5 read the message for bad, with one call and one measure. In general the message has four parts:

  • Calls lists the recursive calls, named a), b), …, each with the argument before and after the call: a) n ~> n div 2 says that a call with argument n leads to a call with argument n div 2.
  • Measures lists the measures Isabelle tried, numbered 1), 2), … .
  • Result matrix has one row for each call and one column for each measure. Each entry says what Isabelle could prove about the measure at that call: < means it decreases, <= that it does not grow (but may stay the same), ? that Isabelle could prove neither, and F that it grows, so that it can never decrease there.
  • Unfinished subgoals are the statements that Isabelle could not prove, each labelled with a call, a measure and a relation: (b, 1, <) is the claim that measure 1 decreases at call b).

A lexicographic order exists when Isabelle can pick measures one after another so that every call has < under one of the picked measures and <= under all the measures picked before it. When no choice works, the message ends with Could not find lexicographic termination order. Exercise 8.8 gives you three more reports to predict and read.

Example 8.2A function nobody has proved terminating

Module 5 ended its section on termination with the Collatz function, which counts the steps that the famous “3n + 1” process takes from n to 1: halve an even number, triple an odd one and add 1. Here is what Isabelle says about it:

Isabellefails on purpose
fun collatz :: "nat ⇒ nat" where
  "collatz n = (if n ≤ 1 then 0
                else if n mod 2 = 0 then collatz (n div 2) + 1
                else collatz (3 * n + 1) + 1)"
Output
consts
  collatz :: "nat ⇒ nat"

Unfinished subgoals:
(b, 1, <):
 1. ⋀n. ⟦¬ n ≤ Suc 0; n mod 2 = Suc 0⟧ ⟹ False
(b, 1, <=):
 1. ⋀n. ⟦¬ n ≤ Suc 0; n mod 2 = Suc 0⟧ ⟹ False

  a) n ~> n div 2

There are two calls and one measure, the size of n. Call a), with n div 2, decreases it: the entry is <. For call b), with 3 * n + 1, the two unfinished subgoals show what Isabelle was left with when it tried to prove that the size decreases (<) or at least does not grow (<=): False, under the conditions of the call, that n is above 1 and odd. Since 3 * n + 1 is larger than n, no proof is possible. (Isabelle writes F only when such a goal becomes plain False, without conditions; here the conditions remain, so the entry is ?.) The row of call b) has no <, so there is no termination order. No other measure is known either: as Module 5 explained, a termination proof would settle the Collatz conjecture, which is still open.

When Isabelle needs help

Some functions terminate, but not by a measure that Isabelle tries. How long must a driver wait for green? From each state, add up the durations until the light turns green:

Isabellefails on purpose
fun wait :: "light ⇒ nat" where
  "wait l = (if l = Green then 0 else duration l + wait (next_light l))"
Output
consts
  wait :: "light ⇒ nat"

Unfinished subgoals:
(a, 1, <):
 1. ⋀l. l ≠ Green ⟹ size (next_light l) < size l
(a, 1, <=):
 1. ⋀l. l ≠ Green ⟹ size (next_light l) ≤ size l
Calls:
  a) l ~> next_light l
Measures:
  1) size
Result matrix:
    1
a:  ?

Could not find lexicographic termination order.

The function does terminate: from any state, the light is green after at most three steps. But the only measure Isabelle tries is the size of l, and every light has size 0 (Definition 8.9). A measure that is always 0 never decreases, so the subgoal for < is false. The subgoal for <= is true, but Isabelle would have to split l into its four cases to prove it, and it does not try; so the entry is ?.

One fix is to write the function so that termination is evident. Here the library does the work: take the first four states, keep those before the first green with takeWhile, and add up their durations. takeWhile P xs is the longest initial part of xs whose elements all satisfy P. The definition is not recursive at all:

Isabelle
definition wait :: "light ⇒ nat" where
  "wait l = sum_list (map duration (takeWhile (λx. x ≠ Green) (trace 4 l)))"

value "map wait [Red, RedAmber, Green, Amber]"
Output
"[32, 2, 0, 35]"
  :: "nat list"

A driver who arrives at amber waits 3 + 30 + 2 = 35 seconds.

When no such reformulation is natural, you can supply the measure yourself. Module 5 met an example: sum_from i n = (if n < i then 0 else i + sum_from (i + 1) n) adds up the numbers from i to n. It terminates because the distance n + 1 - i decreases at every call, but neither argument gets smaller, so fun gives up. The command function separates the definition from its termination proof:

Isabelle
function sum_from :: "nat ⇒ nat ⇒ nat" where
  "sum_from i n = (if n < i then 0 else i + sum_from (i + 1) n)"
  by pat_completeness auto
termination
  by (relation "measure (λ(i, n). n + 1 - i)") auto

function takes the same equations as fun, but leaves proof obligations for you. The line by pat_completeness auto proves that the patterns cover every case and do not contradict each other; with a single equation that is a formality. termination then asks for the termination proof, and you name the measure. λ(i, n). n + 1 - i is the function that maps the pair of arguments (i, n) to n + 1 - i; measure turns it into the relation “has a smaller measure”, and the method relation makes Isabelle use that relation. auto proves the rest: that the relation is well-founded, as it is for every natural-number measure (Module 5), and that the call decreases the measure, from n + 1 - i to n + 1 - (i + 1), because the call happens only when ¬ n < i. Now sum_from is defined, and it computes:

Isabelle
value "sum_from 3 5"
Output
"12"
  :: "nat"

The manual Defining Recursive Functions in Isabelle/HOL, under functions in the Documentation panel, explains function in depth. After termination is proved, these definitions also supply an induction rule that follows the recursion, f.induct; Module 11 uses it.

From HOL to running code

The executable functions you have defined are programs, and Isabelle can translate them into other programming languages: Standard ML, OCaml, Haskell and Scala. This is how a function that you have proved correct becomes part of real software, and Modules 12 and 14 use it for verified programs. Generate Haskell code for the traffic light:

Isabelle
export_code next_light duration trace in Haskell module_name Traffic
Output
See theory exports

export_code takes the names of the functions to translate, and adds everything they need: here the datatype light and the natural numbers. module_name names the Haskell module. Write in SML, in OCaml or in Scala for the other languages. Translation needs executable code equations for the operations involved. For example, exporting the raw definition all_small k = (∀n::nat. n < k) fails with a wellsortedness error: the default code for ∀ enumerates a type in the class enum, and nat is not in that class. This does not mean all_small is uncomputable: it is always False (take n = k), so a proved code equation all_small k = False would make it executable. This distinction matters when turning specifications into running code, as in Module 12.

The code does not appear in the Output panel. In Isabelle/jEdit, the words theory exports in the message are a link: click it, and jEdit’s File Browser opens on the generated files, in a virtual folder whose name begins with isabelle-export:. The Haskell module is the file Traffic.hs, in a folder export1 (export_code numbers the exports of a theory export1, export2, …). Here it is, without its first line, an option for the Haskell compiler, and without the import declarations that follow the module line:

module Traffic(Nat, Num, Light, next_light, trace, duration) where {

data Nat = Zero_nat | Suc Nat;

data Num = One | Bit0 Num | Bit1 Num;

data Light = Red | RedAmber | Green | Amber;

plus_nat :: Nat -> Nat -> Nat;
plus_nat Zero_nat n = n;
plus_nat (Suc m) n = plus_nat m (Suc n);

one_nat :: Nat;
one_nat = Suc Zero_nat;

nat_of_num :: Num -> Nat;
nat_of_num One = one_nat;
nat_of_num (Bit0 n) = let {
                        m = nat_of_num n;
                      } in plus_nat m m;
nat_of_num (Bit1 n) = let {
                        m = nat_of_num n;
                      } in Suc (plus_nat m m);

next_light :: Light -> Light;
next_light Red = RedAmber;
next_light RedAmber = Green;
next_light Green = Amber;
next_light Amber = Red;

trace :: Nat -> Light -> [Light];
trace Zero_nat l = [];
trace (Suc n) l = l : trace n (next_light l);

duration :: Light -> Nat;
duration Red = nat_of_num (Bit0 (Bit1 (Bit1 (Bit1 One))));
duration RedAmber = nat_of_num (Bit0 One);
duration Green = nat_of_num (Bit1 (Bit0 (Bit0 (Bit1 One))));
duration Amber = nat_of_num (Bit1 One);

}

The translation follows your equations closely. The module line names the module Traffic, as module_name asked, and lists what it exports. The datatype light becomes a Haskell data type with the same constructors, and next_light and trace have the same equations as in Isabelle. Everything else is the natural numbers, translated as the logic builds them: a datatype Nat with the constructors Zero_nat and Suc, and numerals in binary, built from One with Bit0 (append the binary digit 0) and Bit1 (append 1). So 30 is Bit0 (Bit1 (Bit1 (Bit1 One))), binary 11110, and nat_of_num converts it into Suc form. This representation is faithful but slow. For efficient code, import the library theory HOL-Library.Code_Target_Nat in the theory header (imports Main "HOL-Library.Code_Target_Nat"): the code generator then represents nat by Haskell’s built-in integers.

Good to know

The code generator is not part of Isabelle’s kernel, so the generated code is not checked by the kernel: the code generator belongs to the trusted base (Module 1). It is designed so that every computation step of the generated program corresponds to rewriting with equations that are theorems in the logic. Provided the generator, its configuration and the target runtime preserve this correspondence, a returned result agrees with the logical definitions; this is a partial correctness guarantee. It does not promise that generated code terminates on every target-language input or avoids resource errors. The command value uses the same machinery. For a term without variables it translates the term into ML, runs it, and turns the result back into a term with term_of; that is why it needs the class term_of (Section 8.6), and why it stopped with an exception at top_value Empty (Section 8.4). For a term with variables, such as rev [a, b, c], it uses a symbolic variant of the same translation.

9

What you learned

  • HOL supports typed functional programming inside a logic. Functions denote total mathematical mappings; the executable definitions here use recursion and have no side effects. typ prints a type, term a term and its type, and value evaluates a term.
  • Types are built from base types (bool, nat, int), type constructors written after their arguments ('a list, 'a option), pairs 'a × 'b, functions 'a ⇒ 'b and type variables. Isabelle infers types; an annotation t :: τ fixes one. In terms, undeclared names can become free variables.
  • λx. t is a function without a name. Functions of several arguments are curried: nat ⇒ nat ⇒ nat means nat ⇒ (nat ⇒ nat), f x y means (f x) y, and a partial application is a function.
  • datatype defines enumerations and recursive types such as stacks and lists. Functions take values apart by pattern matching in equations or with case. Options represent results that may be missing.
  • definition defines non-recursive functions; f_def is not a simplification rule by default. primrec allows primitive recursion; fun allows general patterns and recursion, warns about missing patterns, and resolves overlapping ones in order.
  • The list library offers map, filter, foldr, zip, take, drop, !, [m..<n] and list comprehension. Subtraction on nat is truncated, div and mod are total, and overloaded operations are organised in type classes and sorts.
  • fun requires termination before supplying unrestricted defining equations: accepting arbitrary recursive equations could prove 0 = 1. Isabelle searches for a decreasing measure, reports it, and explains its failure with a matrix of calls and measures. With function and termination you supply the measure yourself.
  • export_code translates definitions into Haskell, SML, OCaml or Scala.

Exercise 8.8★★★Termination in Isabelle’s words

For each definition, predict whether fun accepts it, and what it reports: the termination order, or the entries of the result matrix. Then try it.

  1. merge, which merges two sorted lists into one sorted list, with the type 'a::linorder list ⇒ 'a list ⇒ 'a list and the equations merge [] ys = ys, merge xs [] = xs and merge (x # xs) (y # ys) = (if x ≤ y then x # merge xs (y # ys) else y # merge (x # xs) ys). The class linorder contains the types with a linear order ≤, such as nat and int.
  2. forever n = forever (n + 1), with type nat ⇒ nat. Is it as dangerous as bad in Section 8.7?
  3. count_up i n = (if i < n then count_up (i + 1) n + 1 else 0), with type nat ⇒ nat ⇒ nat, from Exercise 5.8, which fun rejects. Define it with function, as sum_from in Section 8.7, and compute count_up 3 10.
Show solution

  1. Accepted:

    Isabelle
    fun merge :: "'a::linorder list ⇒ 'a list ⇒ 'a list" where
  "merge [] ys = ys"
| "merge xs [] = xs"
| "merge (x # xs) (y # ys) =
     (if x ≤ y then x # merge xs (y # ys) else y # merge (x # xs) ys)"

value "merge [1, 4, 6] [2, 3, 7::nat]"
    Output
    consts
  merge :: "'a list ⇒ 'a list ⇒ 'a list"

Found termination order:
  "(λp. length (snd p)) <*mlex*> (λp. length (fst p)) <*mlex*> {}"

"[1, 2, 3, 4, 6, 7]"
  :: "nat list"

    There are two recursive calls. The first makes the first list shorter and keeps the second; the second call does the opposite. So neither argument’s length alone decreases at both calls. Their sum would be a suitable single measure; Isabelle instead finds a lexicographic order, as for Ackermann’s function in Module 5. It picked the length of the second list first: it decreases (<) at the second call and stays the same (<=) at the first call, where the length of the first list then decreases. Comparing the first lists first would work as well.

  2. Rejected:

    Isabellefails on purpose
    fun forever :: "nat ⇒ nat" where
  "forever n = forever (n + 1)"
    Output
    consts
  forever :: "nat ⇒ nat"

Unfinished subgoals:
(a, 1, <):
 1. False
Calls:
  a) n ~> n + 1
Measures:
  1) size
Result matrix:
    1
a:  F

Could not find lexicographic termination order.

    The call goes from n to n + 1, so the size grows, and the matrix entry is F: the claim that the size does not grow, n + 1 ≤ n, became plain False. No measure can work at all: it would have to decrease from n to n + 1 to n + 2 and so on, an infinite descending chain of natural numbers. But forever is not dangerous in the way bad is: every constant function satisfies forever n = forever (n + 1), so the equation is not contradictory. It is merely not a definition: it does not determine which function forever is, and as a program it runs forever. Like f n = f n in Module 5, it shows that fun rejects every recursion whose termination it cannot prove, whether the equations are contradictory or not.

  3. The measure is n - i. The call happens only when i < n, and then n - (i + 1) < n - i:

    Isabelle
    function count_up :: "nat ⇒ nat ⇒ nat" where
  "count_up i n = (if i < n then count_up (i + 1) n + 1 else 0)"
  by pat_completeness auto
termination
  by (relation "measure (λ(i, n). n - i)") auto

value "count_up 3 10"
    Output
    "7"
  :: "nat"

    count_up i n counts the steps from i up to n, so it equals n - i, here 7.
