Collaborating with Git

Learn to work with branches, remotes, pull requests and merge conflicts — the everyday workflow of most professional software teams — and make your project run from a fresh clone.

1

Why branches?

Everything committed so far has been on a single line of history called main. This works for solo projects, but consider a team scenario:

  • Alice is building the login system
  • Bob is fixing a security bug in the API
  • Charlie is experimenting with a new caching layer

If they all commit to main simultaneously, their changes mix together. Alice cannot test her login system without also getting Bob's half-finished security fix and Charlie's experimental cache. When something breaks, it is hard to tell whose change caused it.

Branches solve this. A branch is an isolated line of development: commits on your branch touch nobody else's work, so there is no interference between people until the work is merged. Alice's login work exists independently from Bob's bug fix. When each is finished and checked, it is merged into main.

What a branch actually is

A branch is not a copy of your files. It is a movable label pointing at a commit; each new commit moves the label of the branch you are on forward one step. main is a branch like any other — teams simply agree to treat it as the shared line. HEAD means 'the branch you are on right now', and git status always tells you which that is. Because a branch is only a label, creating one is instant, which is why Git users branch for everything: a feature, a fix, an experiment.

Creating and switching branches

bash — branch operations
# List local branches (* = current)
git branch
* main

# Create a branch and switch to it in one step (preferred)
git switch -c feature/login
Switched to a new branch 'feature/login'

# Switch back to main (the files in your folder change!)
git switch main

# Rename the current branch
git branch -m feature/user-login

# Delete a branch (must not be current branch)
git branch -d feature/login
   # safe delete: refuses if the branch has unmerged commits
git branch -D feature/login
   # force delete

After creating a branch, any commits you make are on that branch; main is unaffected until you merge. You may see git checkout -b in older tutorials — same effect, but git switch is the clearer, modern command. Switching really does rewrite the files in your folder to match the branch. If uncommitted edits would be overwritten, Git refuses and asks you to commit or stash them first (Section 8).

Lowercase -d is safe because it refuses (error: the branch 'feature/login' is not fully merged) unless the branch's commits are already merged into the current branch or into the remote branch it tracks. Deleting a merged branch removes only the label; the commits stay in main's history.

ℹ main or master?

Git itself still names the first branch of a new repository master, while GitHub uses main. Run git config --global init.defaultBranch main once, before your first git init. If git status says On branch master, git branch -M main renames it.

bash — visualising branches
main:          A --- B --- C
                           \
feature/login:              D --- E

# HEAD -> marks the branch you are on
git log --oneline --graph --all
* 5e6f7a8 (HEAD -> feature/login) Validate the login form
* 4d5e6f7 Add login form
* 3c4d5e6 (main) Add README
* 2b3c4d5 Add app skeleton
* 1a2b3c4 Initial commit

Merging strategies

When a feature branch is ready, switch to the branch you want to merge into (usually main) and run git merge with the branch to bring in. Git uses different strategies depending on the history:

Fast-forward merge

If main has not moved since the branch was created, Git simply slides the main label forward. No merge commit is created and the history stays linear.

bash — fast-forward merge
git switch main
git merge feature/login
Updating 3c4d5e6..5e6f7a8
Fast-forward
 login.py | 42 ++++++++++++++++++++++++++++++++++++++++++
 1 file changed, 42 insertions(+)

Three-way merge

If both branches have new commits, the histories have diverged. Git compares both branch tips with their common ancestor and records the result in a merge commit with two parents. Git opens your editor for the message; the default is fine — save and close.

bash — three-way merge
git merge feature/login
Merge made by the 'ort' strategy.
 login.py | 42 ++++++++++++++++++++++++++++++++++++++++++
 1 file changed, 42 insertions(+)
git log --oneline --graph
*   9f8e7d6 (HEAD -> main) Merge branch 'feature/login'
|\
| * 5e6f7a8 (feature/login) Validate the login form
* | 7c8d9e0 Fix typo in README
|/
* 3c4d5e6 Add README

Git merges automatically when the two sides changed different files, or different lines of the same file. Only when both changed the same lines does it stop and ask you — a merge conflict (Section 6).

Remote repositories in depth

A remote is simply another copy of your repository hosted elsewhere — usually GitHub, where the whole team can reach it. The default remote is named origin by convention, and git clone creates it for you. Four verbs move commits between copies: clone copies, fetch looks, pull updates, push publishes. Your commits stay on your machine until you push — committing is not backing up; pushing is.

bash — working with remotes
# Clone an existing repository (creates origin)
git clone https://github.com/user/repo.git

# See configured remotes
git remote -v
origin  https://github.com/user/repo.git (fetch)
origin  https://github.com/user/repo.git (push)

# Download changes without merging (safe: no files change)
git fetch origin

# Download and merge in one step (do this before you start work)
git pull

# First push of a new branch: -u sets up tracking
git push -u origin feature/login
 * [new branch]      feature/login -> feature/login
branch 'feature/login' set up to track 'origin/feature/login'.

# Afterwards, plain git push and git pull know where to go
git push

A fork is your own copy of someone else's repository on GitHub, under your account (forking copies GitHub → GitHub; cloning copies GitHub → your machine). Clone your fork rather than the original so that origin is a repository you are allowed to push to — git remote -v should show your username.

ℹ fetch vs pull

git fetch downloads changes and updates origin/main (your view of the remote) but does NOT modify your branches or files. It is always safe. git pull fetches and then immediately merges, so your files change. Defaulting to pull is fine on small projects; to look first, run git fetch, then git log --oneline main..origin/main to list incoming commits, then git merge origin/main.

If git pull stops with fatal: Need to specify how to reconcile divergent branches, both sides have new commits and Git wants to know whether to merge or rebase. This series always merges: run git config --global pull.rebase false once and pull again (the Git for Windows installer normally sets this already).

⚠ Pushing over HTTPS: tokens, not passwords

GitHub rejects account passwords for Git over HTTPS. When you first push, either Git Credential Manager (bundled with Git for Windows) opens a browser so you can sign in, or Git prompts for a username and password: enter your GitHub username and paste a personal access token at the password prompt. Create one at GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens, with access to the repository and Contents: Read and write. The paste shows nothing on screen — that is normal. Treat the token like a password: never store it in a file in your repository.

5

The pull request workflow

A pull request (PR) is a request to merge your branch into main. It is opened on GitHub, not typed into Git — a hosting-platform feature rather than a Git concept (GitLab calls it a merge request). The PR page holds the diff, a description, comments, reviews and automated check results. It is the standard collaborative workflow in most professional teams.

  1. Create a branch for your work: git switch -c add-multiply
  2. Make commits on the branch as you work.
  3. Push the branch to GitHub: git push -u origin add-multiply
  4. Open a PR on GitHub with a clear description (below). In a fork, GitHub aims the PR at the original repository by default; when practising, change the base to your own fork's main.
  5. Review happens — teammates comment on the diff and ask questions. Respond by committing on the same branch and pushing: a PR tracks the branch, so new commits appear on it automatically.
  6. CI checks run automatically on every push and report pass/fail on the PR — the pipeline you will build in Module 6.
  7. Approval and merge — once approved and all checks pass, merge the PR (the default Create a merge commit is fine). Then update your machine with git switch main and git pull, and delete the branch on GitHub and with git branch -d add-multiply.
◆ Good PR descriptions

A good pull request description answers three questions, so the reviewer does not have to reverse-engineer your intent from the diff:

  • What — what exactly changed?
  • Why — what problem does it solve? Link to the requirement, issue or ticket.
  • How to test — a concrete command and the expected result.

A bad description is 'fixed stuff'. A good one: What: adds multiply() and a menu entry. Why: implements requirement R3 from the project plan. How to test: run ./run.sh, choose option 3, enter 6 and 7, expect 42.

Code review

A review means someone spent their time making your work better. Review the code, not the person ('this function could…', never 'you always…'). As a reviewer, be specific and kind, and praise the good parts too — 'looks good' alone teaches nobody anything. As the author, do not defend; ask questions, because reviewers see what you cannot. This is CALMS in practice: a blameless culture, and knowledge shared between author and reviewer.

⚠ Rewrite only what you have not pushed

git commit --amend replaces the last commit — fine while it exists only on your machine. Once pushed, treat a commit as permanent: amending it makes your next push fail, and the usual online 'fix', git push --force, overwrites history on the server and can delete other people's work. Make a new commit instead.

CI checks and the fresh-clone test

Review is a human safety net; continuous integration adds an automated one. Once CI is set up, every push triggers checks on a server and the PR shows a green tick (all passed) or a red cross (something to fix); they re-run on every push. Many teams treat the green tick as a precondition for merging — no tick, no merge. Module 5 explains the checks; Module 6 automates them with GitHub Actions.

Automation needs a project that runs in a standard way from a clean copy. Keep the code, a README.md saying how to run it, and a one-command start script together in the repository, with .gitignore keeping __pycache__/, *.pyc and .env out. Then clone it somewhere new and run it — no edits, no secret steps:

bash — run.sh and the fresh-clone test
# run.sh (make it executable once: chmod +x run.sh)
#!/bin/bash
python3 calculator.py

# The fresh-clone test
cd /tmp
git clone https://github.com/your-username/calculator.git
cd calculator
./run.sh

Anything that only works in your original folder — an uncommitted file, a hard-coded path, a missing execute bit — fails here, cheaply. If it runs from a fresh clone for you, it runs for a teammate and for a CI server, which is just a very pedantic teammate doing a fresh clone every time. Two tips: stage files by name (git add run.sh README.md) rather than git add ., so nothing unintended is swept in; and remember Git records the execute bit as of the commit, so on Windows use git add --chmod=+x run.sh.

Merge conflicts step by step

A merge conflict occurs when two branches have changed the same lines of the same file (or one deleted a file the other edited). Git is not broken and nothing is lost: it refuses to guess which change should win, writes both versions into the file, and asks you to choose. Every developer meets conflicts; calm beats panic.

bash — creating a conflict scenario
# On main: someone changes a function
# main: app.py line 15: return user.name.upper()

# On feature/login: you change the same line
# feature: app.py line 15: return user.name.strip()

# Merging triggers a conflict
git merge feature/login
Auto-merging app.py
CONFLICT (content): Merge conflict in app.py
Automatic merge failed; fix conflicts and then commit the result.
plain — what a conflict looks like
<<<<<<< HEAD
    return user.name.upper()
=======
    return user.name.strip()
>>>>>>> feature/login

<<<<<<< HEAD opens your side — the branch you are on (here main). ======= divides the two versions. >>>>>>> feature/login closes their side — the branch being merged in.

  1. Open the conflicted file in your editor. git status lists every unresolved file under Unmerged paths.
  2. Understand both sides and why they differ.
  3. Edit the file to the correct final state — keep what should be there and delete all three marker lines. Leftover markers are not code and will break the program.
  4. Check it: run the program or tests; grep -n '<<<<<<<' app.py should print nothing.
  5. Stage the file to mark it resolved: git add app.py
  6. Complete the merge: git commit (Git pre-fills a merge commit message)
⚠ Conflicts require thought

Do not just pick one side automatically — 'pick mine and hope' is how teams silently delete each other's fixes while the merge looks successful. Sometimes the correct resolution combines both changes:

python
    return user.name.strip().upper()  # both: strip whitespace AND uppercase

Equally, do not delete the markers and leave both versions stacked up: Git will happily commit nonsense. Read the result as if you had written it fresh, and if you are unsure, ask the author of the conflicting change. Panicking? git merge --abort puts everything back as it was before the merge.

Conflicts when you push

In a team, conflicts usually surface at push time. If someone pushed to the same branch first, Git rejects your push (Updates were rejected because the remote contains work that you do not have locally). Run git pull to merge their commits into yours, resolve any conflict as above, commit, and push again. Never use git push --force to make the rejection go away: it would discard their commits on the server.

7

Branch strategies in teams

Teams adopt conventions for how branches are named and how work flows. Two common models:

Feature branch workflow

Every piece of work gets its own branch. All work flows through PRs into main. Main is always deployable. This is the most common model for teams of any size, and the one this series uses. Keep branches short-lived: the longer one lives apart from main, the harder the eventual merge.

plain — feature branch naming
feature/user-login
feature/JIRA-1234-search-api
fix/login-null-check
hotfix/critical-security-patch
chore/update-dependencies
add-multiply                  # plain descriptive names suit small projects

Trunk-based development

Developers integrate into main (the trunk) very frequently — at least daily — either directly or through branches that live for hours rather than weeks. Unfinished features are hidden behind feature flags until ready. This requires strong CI and a culture of very small commits. Google is a well-known example at very large scale.

ℹ Out of scope here

Rebasing, interactive rebase, cherry-pick and branch protection rules are deliberately left out of this module. If you meet git rebase online, set it aside for now: merging is all you need in this series.

8

git stash for context switching

You are halfway through a change when an urgent bug fix arrives, and Git will not let you switch branches because your uncommitted edits would be overwritten. You do not want to commit half-finished work. git stash parks your changes so you can switch context. It is a convenience, not a core skill: committing on a branch is always fine too.

bash — git stash
# Save uncommitted changes to tracked files (staged and unstaged)
git stash

# Save with a descriptive name; add -u to include new untracked files
git stash push -m "half-built login form"
git stash push -u

# List stashed changes
git stash list
stash@{0}: On feature/login: half-built login form
stash@{1}: WIP on main: ...

# Restore the most recent stash (and remove it from the list)
git stash pop

# Apply without removing from the list
git stash apply

# Apply a specific stash
git stash apply stash@{1}

# Discard a stash
git stash drop

Key terms

branch
An isolated line of development: a movable label pointing at a commit.
HEAD
The branch you are on right now.
merge
Combining the history of one branch into another.
fast-forward
A merge where the target branch just moves its pointer forward — no merge commit created.
merge commit
A commit with two parents, created when two diverged branches are combined.
remote
A copy of the repository hosted elsewhere. Default is called origin.
fork
Your own copy of someone else's repository on GitHub, under your account.
git fetch
Download changes from the remote without merging. Safe to run anytime.
git pull
Fetch plus merge. Equivalent to git fetch followed by git merge.
pull request
A request, opened on GitHub, to review and merge a branch (GitLab: merge request).
merge conflict
Both branches changed the same lines of a file; a person decides the result.
fresh-clone test
Clone the repository somewhere new and run it, to prove it needs no local setup.
git stash
Temporarily save uncommitted changes so you can switch context.
tracking branch
A local branch linked to a remote branch. Set with git push -u.

Exercises

✎ Lab exercises — approximately 2 hours

Everything here can be done on your own. Where teamwork needs two people, you play both roles, using two branches or two clones.

Part A: Branching

  1. Fork the starter repository your course provides — or create a GitHub repository with a README and a file motto.txt containing the single line DevOps is about tools. — and clone your copy. Check git remote -v and git log --oneline.
  2. Create and switch to a branch called add-<your-name>-greeting.
  3. Add a file greetings.py that prints a greeting. Commit it with a deliberately vague message, then fix the message with git commit --amend -m "Add greeting for <your-name>". Why is amending acceptable only before a push?
  4. Make a second commit with a good message. Use git log --oneline --graph --all to visualise the branch structure, then switch to main and notice your changes are not there.

Part B: Remotes and pull requests

  1. Push your branch with git push -u origin add-<your-name>-greeting (sign in through the browser or use a token if asked).
  2. Open a pull request into your own repository's main with a What / Why / How to test description.
  3. Review it as if you were a teammate: on Files changed, leave one specific, constructive comment on a line.
  4. Switch roles: as the author, reply, make the change locally on the same branch, commit and push. Why did the PR update by itself?
  5. Merge the PR on GitHub. Back locally, switch to main and run git pull to get the merged changes.
  6. Delete the branch on GitHub and with git branch -d. Why is -d safe?

Part C: Conflict resolution

  1. From main, create motto-a, change the line in motto.txt to DevOps is about collaboration., commit, and switch back to main. Then create motto-b from main and change the same line to DevOps is about automation.; commit and switch back.
  2. Run git merge motto-a (a fast-forward — why?), then git merge motto-b, which conflicts. Read git status and identify which side is HEAD.
  3. Resolve the conflict thoughtfully (for example, DevOps is about collaboration and automation.), delete all three markers, stage and complete the merge commit, and push.
  4. Now play two people: clone the repository again into a folder called teammate-copy, change the motto there, commit and push. In your original clone, change the same line differently, commit, and try to push — it is rejected. Pull, resolve, commit and push.

Part D: Your own project

  1. In your own project (for example the calculator from Module 3), create a branch add-run-script and add an executable run.sh, a README line saying how to run it, and a .gitignore covering __pycache__/ and .env.
  2. Stage the files by name, commit, push, open and merge a PR, then update your local main.
  3. Run the fresh-clone test in /tmp. If anything fails, fix it, push, and test again.

Part E: git stash (optional)

  1. Start editing a file but do not commit.
  2. Use git stash to save your changes. Verify with git status that the working directory is clean.
  3. Make and commit a change to a different file. Then use git stash pop to restore your original changes.
  4. Verify both changes are now present.
