Continuous Integration and Automated Testing

Understand why CI exists, what a pipeline does, how automated tests are written and read, and how to turn a test suite into a local quality gate.

Integration hell and CI's solution

In 2000, a software team might spend three months developing features independently, then convene for a week-long integration sprint — a period of intense, stressful debugging as all the branches were merged and the inevitable conflicts resolved. This was called integration hell. The painful merge day is not the disease but a symptom of integrating rarely: the longer code lives apart, the further it drifts, and the pain grows faster than the time apart.

The observation that made CI possible was simple: if integration is painful because you do it rarely, do it constantly — the maxim 'if it hurts, do it more often', popularised by Jez Humble and David Farley's book Continuous Delivery. If you merge every change quickly and check it automatically, integration never accumulates into a crisis.

Continuous Integration is a practice plus a machine. The practice: every developer merges small changes into the shared main line at least once per day. The machine: every push automatically triggers a build and test run, so problems are caught within minutes, while the change is still fresh, and nobody has to remember to run the checks. A team with a CI server but month-old branches has bought the machine and skipped the practice.

What CI is not

CI is frequently confused with CD (Continuous Delivery or Continuous Deployment). They are related but distinct:

PracticeWhat is automatedHuman release decisionNeeds
Continuous IntegrationBuild and test every pushPeople release and deploy manuallyA test suite and a CI service
Continuous DeliveryCI plus release preparation: every passing change is releasable at any timeA person decides when to deployAutomated release steps
Continuous DeploymentCI plus automatic deployment of every passing change to productionNone — no release actionAutomated tests the team trusts

In this module we focus on CI. Delivery and deployment are covered in Modules 9 and 10.

The CI feedback loop

A CI pipeline is a fixed sequence of automated stages, run in the same order on every push and every pull request — no exceptions, no favours. Every CI system, regardless of which tool you use (GitHub Actions, Jenkins, CircleCI, GitLab CI), follows the same loop:

Push / PR
→
Checkout
→
Install deps
→
Lint
→
Test
→
Build
→
✓ or ✗ on the PR
Checkout
Clone the repository at your exact commit onto a fresh, empty machine — not yours.
Install deps
Install what the project declares it needs (e.g. pip install -r requirements.txt). Anything undeclared or uncommitted fails here.
Lint
A linter (e.g. flake8 or ruff) reads code without running it and flags unused variables, undefined names and likely typos.
Test
Run the automated test suite — the heart of the pipeline.
Build
Assemble what you would ship: almost nothing for a small Python project, very real for compiled code or container images.

Each stage must pass before the next starts: if any step returns a non-zero exit code, the pipeline stops and reports a red cross. Cheap, fast checks go first, so a broken change fails in seconds rather than minutes. When a red result blocks a merge, the pipeline is acting as a quality gate (Section 9).

ℹ Where this module stops

In this module you run the checks yourself, with a local quality-gate script (Section 9). Module 6 moves the same command onto GitHub Actions so that it runs automatically on every push.

The cost of slow feedback

The value of CI is in the speed of the feedback. Consider:

Feedback speedCost of fixing the bug
Within 5 minutes (CI)Minutes — change is fresh, easy to identify
End of day (code review)Hours — context lost, others may have built on top
Next sprint (QA testing)Days — may require significant rework
In production (user report)Very high — user impact, potential data issues, emergency fix required

Exact costs vary; the direction does not: the longer a fault goes unnoticed, the harder it is to find and fix.

Anatomy of a test

An automated test is a program that calls your code with specific inputs and verifies the outputs match expectations. It is an executable specification: a requirement such as 'add returns the sum of two numbers', written so a machine can check it on every change — unlike a written specification, it fails loudly when the code stops meeting it. The Arrange-Act-Assert pattern gives every test a consistent structure:

python — arrange, act, assert
from calculator import add

def test_add():
    # ARRANGE: set up the inputs
    a, b = 2, 3

    # ACT: call the code under test
    result = add(a, b)

    # ASSERT: check the answer
    assert result == 5

The assert statement raises an AssertionError if the condition is false. pytest catches this and marks the test as failed.

Testing edge cases

Testing only the happy path (expected input, expected output) is insufficient. Good tests also cover:

  • Boundary values — what happens with the smallest or largest valid input?
  • Empty or zero input — what happens with an empty list, an empty string, or zero?
  • Unusual values — negative numbers, results that are not whole numbers.
  • Error conditions — does the function raise the right exception when it should?
python — testing edge cases and exceptions
import pytest
from calculator import add, multiply, divide

def test_divide_uneven():
    # Arrange: numbers that do not divide evenly
    a, b = 5, 2
    # Act: call the function under test
    result = divide(a, b)
    # Assert: we expect the exact decimal answer
    assert result == 2.5

def test_add_negatives():
    assert add(-2, -3) == -5

def test_multiply_by_zero():
    assert multiply(7, 0) == 0

def test_divide_by_zero_raises():
    # Python's / raises ZeroDivisionError; check that it does
    with pytest.raises(ZeroDivisionError):
        divide(5, 0)

pytest.raises asserts that an exception should happen. Without it, assert divide(5, 0) == 0 never reaches the comparison: the call crashes with ZeroDivisionError, which pytest reports as the reason for the failure.

⚠ Comparing decimals

divide(5, 2) == 2.5 is safe because 2.5 is exactly representable in binary floating point, but == on floats is not safe in general: in Python, 0.1 + 0.2 gives 0.30000000000000004. For results like one-third, compare approximately: assert divide(1, 3) == pytest.approx(0.3333, abs=1e-4).

The testing pyramid

Not all tests are equal. The testing pyramid describes three layers of automated tests, with different trade-offs of speed, scope, and cost.

plain — testing pyramid
           /\
          /  \
         / E2E\  ← few, slow, expensive
        /------\
       /Integr. \  ← some, medium
      /----------\
     /    Unit    \  ← many, fast, cheap
    /______________\
LayerTestsSpeedCalculator example
UnitOne function or class, called directly, in isolationMillisecondsadd(2, 3) == 5
IntegrationSeveral components working togetherSecondsthe input parser and the maths together: the text "2 + 3" gives 5
End-to-endThe entire system from the user's perspectiveSeconds to minuteslaunch the app, type 2 + 3, see 5 on screen

assert divide(6, 2) == 3 is a unit test: one function, called directly and checked in isolation. (Combining two arguments is not combining components.) For this module, we focus on unit tests. They run in milliseconds, require no infrastructure, and give precise feedback on exactly which function is broken.

5

pytest in practice

pytest is Python's de facto standard testing library. Install it with python3 -m pip install pytest, and run it as python3 -m pytest so it uses the same Python and sidesteps PATH problems. It discovers tests automatically: any file matching test_*.py or *_test.py, and any function whose name starts with test (conventionally test_). A function called check_add or a file called tests.py is silently ignored, so always read the collected N items line first: no tests ran is a naming problem, not success.

bash — running tests
# Run all tests
python3 -m pytest

# Verbose output — show each test name
python3 -m pytest -v

# Run a specific test by name
python3 -m pytest test_calculator.py::test_divide

# Stop after first failure
python3 -m pytest -x

# Show local variables on failure
python3 -m pytest -l

# Run tests whose names match a keyword expression
python3 -m pytest -k "divide or multiply"
plain — pytest output (passing)
============================= test session starts =============================
collected 4 items

test_calculator.py::test_add PASSED                                      [ 25%]
test_calculator.py::test_subtract PASSED                                 [ 50%]
test_calculator.py::test_multiply PASSED                                 [ 75%]
test_calculator.py::test_divide PASSED                                   [100%]

============================== 4 passed in 0.01s ==============================

Without -v, the middle collapses to test_calculator.py ...., one dot per passing test. When every test passes, pytest exits with code 0 — which is how a pipeline knows to show a green tick.

Reading a failure

Here divide has been broken on purpose so that it returns a * b:

plain — pytest output (failing)
test_calculator.py::test_add PASSED                                      [ 25%]
test_calculator.py::test_subtract PASSED                                 [ 50%]
test_calculator.py::test_multiply PASSED                                 [ 75%]
test_calculator.py::test_divide FAILED                                   [100%]

================================== FAILURES ===================================
_________________________________ test_divide _________________________________

    def test_divide():
>       assert divide(6, 2) == 3
E       assert 12 == 3
E        +  where 12 = divide(6, 2)

test_calculator.py:13: AssertionError
=========================== short test summary info ===========================
FAILED test_calculator.py::test_divide - assert 12 == 3
========================= 1 failed, 3 passed in 0.04s =========================

Read it in order: which test failed (only test_divide, so the damage is confined to division); expected vs actual (the > marks the failing assertion, and the E lines show the code returned 12 where the test expected 3, from the call divide(6, 2)); and where (test_calculator.py:13 is the assertion; the bug is in the function under test — 6 × 2 = 12 gives it away). Any failure makes pytest exit with a non-zero code, which a pipeline turns into a red cross.

✖ Fix the code, not the test

A failing test is evidence. Usually the code is wrong: correct it and run the whole suite again. Change a test only when the requirement has changed. Editing the test to expect the wrong answer, commenting out the assert 'until after the deadline' or deleting the test turns the suite green while the program stays broken.

⚠ Collection fails with a stdin error

Importing a module runs its top-level code. If calculator.py calls input() outside a function, collection fails with OSError: pytest: reading from stdin while output is captured! Move the interactive code into main() and call it only under if __name__ == "__main__":. Do not add -s as the message suggests: the run would then wait for input.

Going further: parametrised tests and fixtures

The tests above are enough for a small project: a few honest assertions you can explain beat a hundred clever ones you cannot. Two pytest features help as a suite grows; treat them as optional extras.

Parametrised tests run one test function against several cases, each reported as its own test — the cure for copy-pasted, near-identical tests:

python — pytest.mark.parametrize
import pytest
from calculator import add

@pytest.mark.parametrize("a, b, expected", [
    (2, 3, 5),
    (-2, -3, -5),
    (0, 0, 0),
])
def test_add_many(a, b, expected):
    assert add(a, b) == expected

# pytest -v reports three tests:
# test_add_many[2-3-5]  test_add_many[-2--3--5]  test_add_many[0-0-0]

Many tests need the same setup — a configured object, a sample user. Copying it into every test is repetitive; a fixture defines it once, and pytest passes it to any test that names it as a parameter:

python — pytest fixtures
import pytest

# Define a fixture
@pytest.fixture
def sample_user():
    return {
        'username': 'alice',
        'email': 'alice@example.com',
    }

# Use the fixture as a parameter
def test_create_greeting(sample_user):
    result = create_greeting(sample_user)
    assert 'alice' in result

def test_user_has_email(sample_user):
    assert '@' in sample_user['email']

Reading CI output like a pro

A CI log can be hundreds of lines. Finding the failure quickly is a critical skill, and the same process works on your own terminal before any pipeline exists:

  1. Find the step that failed — pipeline tools highlight failed steps in red. Click it to expand.
  2. Scroll to the first error — not the last. The first error often causes the subsequent errors.
  3. Identify the type of failure — is it a syntax error? An import error? A test assertion failure? An environment error?
  4. Note the file and line number — always shown for Python errors.
  5. Reproduce locally — run the exact same command the pipeline ran (for example ./check.sh), fix the cause, and push again. Re-running unchanged code, or opening a fresh PR and hoping, does not fix anything.
8

Common failure patterns

ModuleNotFoundError
A package is missing: add it to requirements.txt and install it in the pipeline. Or the test cannot find your code: test_calculator.py belongs next to calculator.py.
No module named pytest
pytest is not installed in that environment (or pytest: command not found). Fix: python3 -m pip install pytest locally, or in the pipeline's install step.
collected 0 items
Nothing matched pytest's naming rules. Check file names (test_*.py) and function names (test_…). pytest exits with code 5 here, so a gate treats it as a failure.
Permission denied: ./check.sh
The script is not executable in the commit. Fix: chmod +x check.sh and commit again (on Windows: git add --chmod=+x check.sh).
YAML parse error
From Module 6: a mistake in the workflow file, usually indentation. YAML does not allow tabs for indentation.
AssertionError
A test failed. Read the output — it shows what was expected vs what was returned.
Connection refused
A test is trying to connect to a database or service that is not running in CI. Unit tests should not need network connections.

Quality gates

A quality gate is a rule the pipeline enforces: no merge into main until every agreed check passes, so a red cross blocks the merge and main stays green — anyone can pull it and trust it. Review and gate are partners: reviewers judge design and intent; the gate checks facts. A green tick does not promise perfect code, only that every automated check passed on a neutral machine. Common quality gates include:

  • All tests must pass
  • Code style must conform (e.g. flake8, black --check)
  • No known security vulnerabilities in dependencies
  • Test coverage does not drop below a threshold the team agrees
  • No secrets or credentials in the code

On GitHub, gates are enforced with branch protection rules that require CI checks to pass before a PR can be merged; configuring them is beyond this module.

Build a local quality gate

Before any server runs your checks, you can build the gate yourself. Put the test command in a script that reports success only when the whole suite is green:

bash — check.sh
#!/bin/bash
set -euo pipefail

echo "=== Calculator quality gate ==="
python3 -m pytest -v
echo "QUALITY GATE PASSED"
bash — the gate passing, then failing
chmod +x check.sh
./check.sh
...
5 passed in 0.01s
QUALITY GATE PASSED
echo $?
0

# Sabotage subtract (return a + b), then run the gate again
./check.sh
...
FAILED test_calculator.py::test_subtract - assert 8 == 2
1 failed, 4 passed in 0.05s
echo $?
1

set -euo pipefail (Module 2) stops the script at the first failing command, so when pytest fails the success line never prints and the script exits non-zero — which is why the success message comes last. Check $? immediately, before another command replaces it. That exit code is the whole interface: a CI server can run ./check.sh on every push and let the change through only when it returns 0, which is what Module 6 sets up with GitHub Actions. Commit the suite and the gate once they pass, staging files by name: pytest creates __pycache__/ and .pytest_cache/, which belong in .gitignore.

bash — commit the passing suite
git status
git add test_calculator.py check.sh
git commit -m "Add automated test quality gate"
git push

When the build goes red

A red main build is the team's top priority. Whoever pushed the breaking change fixes or reverts it, and nobody piles more work on top, or no one can tell whose change broke what. Breaking the build is not shameful — the pipeline caught it, so the system worked; in a blameless culture you fix it, then ask which check was missing. A pipeline everyone ignores is worse than none: red must mean stop, like the andon cord on a Toyota production line.

Key terms

CI
Continuous Integration — frequently merging code and automatically verifying each change.
continuous delivery
CI plus release preparation: every passing change is releasable; a person decides when to deploy.
continuous deployment
Every passing change is released to production automatically.
pipeline
Ordered automated stages — checkout, install, lint, test, build — run on every push.
lint
Checking code without running it for mechanical problems such as unused or undefined names.
exit code
The number a command returns: 0 for success, non-zero for failure. Pipelines act on it.
quality gate
A check that must pass before code can merge into a protected branch.
unit test
A test of an isolated function or class, with no external dependencies.
Arrange-Act-Assert
The three-part shape of a test: set up inputs, call the code, check the result.
assert
A statement that raises AssertionError if a condition is false.
pytest
Python's de facto standard testing library and test runner.
testing pyramid
Unit (many, fast) → Integration (some) → E2E (few, slow).
test fixture
Shared setup code that multiple tests can use, defined with @pytest.fixture.
feedback loop
The time between making a change and knowing whether it broke something.

Sample question types

Write the Git command that creates a branch called feature/search and immediately switches to it.
Answer: git switch -c feature/search
A developer runs git diff. There is no output. They then run git diff --staged and see changes. Explain the state the repository is in.
The changes have been staged (git add has been run) but not yet committed. git diff compares the working directory to the staging area; since they match, it shows nothing. git diff --staged compares the staging area to the last commit, where the changes are visible.
Which command downloads new commits from GitHub but changes none of the files in your working directory: git pull, git fetch, git push or git clone?
git fetch. It updates origin/main but leaves your branches and files alone; git pull would also merge the commits into your current branch.
What does set -euo pipefail at the top of a shell script do?
-e makes the script exit immediately if a command returns a non-zero exit code; -u treats unset variables as errors; -o pipefail makes a pipeline fail if any command in it fails, not only the last. Without them, a script can carry on after a failed step, causing misleading or dangerous behaviour.
Describe the CALMS framework in your own words.
CALMS stands for Culture (shared responsibility and blameless post-mortems), Automation (replace repetitive manual steps with scripts and machines), Lean (eliminate waste, prefer small frequent changes), Measurement (track delivery metrics to identify improvements), and Sharing (knowledge, tools, and post-mortems cross team boundaries).
