Git and GitHub, Step by Step

Lesson 11Undo and fix mistakes

The commands that get you out of trouble, as recipes. Try each one on your project, so you know what to do when it happens for real.

⏱ 40 minYou need: Lesson 10 (my-page on GitHub, up to date)

In this lesson you will

  • Take a file out of the staging area with git restore --staged
  • Keep files out of Git with .gitignore
  • Fix your last commit with git commit --amend, before you push
  • Undo your last commit but keep the work, with git reset --soft
  • Undo a commit that is already on GitHub, with git revert
  • Find “lost” commits with git reflog
1

Two rules first

Git almost never loses work that you have committed. Most “disasters” can be undone. Two rules keep it that way:

Key idea
  1. Commit before you try anything risky. What is committed can be recovered; changes that were never committed cannot.
  2. Only rewrite commits that you have not pushed. --amend and reset change your history. That is fine on your computer, but if GitHub already has those commits, use git revert instead.

Open my-page in VS Code with a terminal. Each recipe below is headed by the situation it is for.

2

“I want to throw away my changes to a file”

You met this in Lesson 4: git restore FILE throws away the changes to a file that you have not staged, and puts it back as it was in your last commit. If you have already staged the changes with git add, run git restore --staged FILE first (see “I added a file I did not mean to”, below). The same command also brings back a file you deleted by mistake. There is nothing to try now: you did this in Lesson 4.

Terminal
$ git restore index.html

Remember that the changes you throw away cannot be recovered.

3

“I want a file as it was in an older commit”

Find the commit in git log --oneline, then give its hash to git restore --source. For example, to get index.html as it was in your very first commit (use a hash from your own list):

Terminal
$ git restore --source c50e3a0 index.html

Your file now looks as it did then. Nothing else has changed: if you want to keep the old version, git add and git commit it as a new change; if not, git restore index.html takes you back to your last commit. You do not need to try it now.

4

“I added a file I did not mean to”

Suppose you keep private notes in the project folder. Create a file notes.txt:

notes.txt
Ideas for my page:- add a photo- try a different font

Out of habit, you add everything:

Terminal
$ git add .$ git statusOn branch main
Your branch is up to date with 'origin/main'.

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	new file:   notes.txt

The notes are about to go into a commit, and then to GitHub, where anyone can read them. The hint says how to take a file back out of the staging area:

Terminal
$ git restore --staged notes.txt$ git statusOn branch main
Your branch is up to date with 'origin/main'.

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	notes.txt

nothing added to commit but untracked files present (use "git add" to track)

notes.txt is untracked again. --staged only changes the staging area; your file is untouched. To take everything out of the staging area at once, use git restore --staged ..

5

“Git should never track this file”

notes.txt is safe for now, but the next git add . would add it again. To tell Git to ignore a file for good, list it in a file called .gitignore (with a dot at the start). Create it in my-page, next to index.html, the way you created README.md:

.gitignore
# My private notesnotes.txt

Lines starting with # are comments. Every other line is the name of a file, or a pattern, to ignore.

Terminal
$ git statusOn branch main
Your branch is up to date with 'origin/main'.

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	.gitignore

nothing added to commit but untracked files present (use "git add" to track)

notes.txt has disappeared from the list: Git ignores it now, and VS Code shows it greyed out. .gitignore itself is a normal file that belongs in the project, so commit it:

Terminal
$ git add .gitignore$ git commit -m "Ignore my private notes"[main 5841c42] Ignore my private notes
 1 file changed, 2 insertions(+)
 create mode 100644 .gitignore
Tip

.gitignore takes patterns too: *.log ignores every file ending in .log, and drafts/ ignores a whole folder.

Watch out

.gitignore only works for files Git does not track yet. A file you have already committed stays tracked until you run git rm --cached FILE and commit. And anything you have pushed stays in the history on GitHub: if a password got there, change it.

6

“My last commit has a mistake, and I have not pushed it”

You add one more hobby, and some space between the list items. Change both files:

index.htmlhighlighted: the lines to add or change
<!DOCTYPE html><html lang="en"><head>  <meta charset="utf-8">  <title>About me</title>  <link rel="stylesheet" href="style.css"></head><body>  <h1>Welcome to my page!</h1>  <p>This is my first web page, published with GitHub Pages.</p>  <p>I like walking, photography and good coffee.</p>  <h2>My hobbies</h2>  <ul>    <li>Walking</li>    <li>Photography</li>    <li>Cooking</li>    <li>Reading</li>  </ul>  <h2>Contact</h2>  <p>You can find me on GitHub as your-username.</p></body></html>
style.csshighlighted: the lines to add or change
body {  font-family: sans-serif;  max-width: 40em;  margin: 2em auto;  padding: 0 1em;  background: #1e1e2e;  color: #e6e6e6;} h1 {  color: #8ec5fc;} li {  margin-bottom: 0.3em;}

Then you commit in a hurry: only one file, and a typo in the message.

Terminal
$ git add index.html$ git commit -m "Add redaing to my hobbies"[main b0c7144] Add redaing to my hobbies
 1 file changed, 1 insertion(+)

Two mistakes: “redaing”, and style.css was left out. Because you have not pushed this commit, you can fix it. Add the forgotten file, then use --amend with the right message:

Terminal
$ git add style.css$ git commit --amend -m "Add reading to my hobbies"[main cab53b1] Add reading to my hobbies
 Date: Thu Nov 12 10:09:00 2026 +0000
 2 files changed, 5 insertions(+)

--amend replaces your last commit with a new one, made from what it had plus what is staged now, and with the new message. Date: shows that it keeps the time of the original commit. Check:

Terminal
$ git log --oneline -2cab53b1 (HEAD -&gt; main) Add reading to my hobbies
5841c42 Ignore my private notes

The commit with the typo is gone from your history. Notice that the hash changed: it is a new commit.

Tip

To add a forgotten file without changing the message, use git commit --amend --no-edit.

7

“I want to undo my last commit, but keep the work”

Sometimes you want the commit gone, but not the changes: to change them more, or to commit them differently. As long as you have not pushed, git reset --soft takes the last commit back and leaves its changes staged. --soft means “keep the changes”, and HEAD~1 means “one commit before HEAD”. The ~ is a tilde: on some keyboards you press it and then Space. If you cannot find it, use the Copy button.

Terminal
$ git reset --soft HEAD~1$ git statusOn branch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified:   index.html
	modified:   style.css

The commit “Add reading to my hobbies” is undone, but its changes are waiting in the staging area, so nothing is lost. (“Ahead by 1 commit” is the .gitignore commit, which you have not pushed yet.) Commit them again. Here you commit them unchanged, to see that nothing was lost; in real life you would change something first, or commit the files separately.

Terminal
$ git commit -m "Add reading to my hobbies"[main dc4f482] Add reading to my hobbies
 2 files changed, 5 insertions(+)

And push both commits:

Terminal
$ git pushEnumerating objects: 10, done.
Counting objects: 100% (10/10), done.
Delta compression using up to 8 threads
Compressing objects: 100% (6/6), done.
Writing objects: 100% (7/7), 856 bytes | 856.00 KiB/s, done.
Total 7 (delta 2), reused 0 (delta 0), pack-reused 0 (from 0)
remote: Resolving deltas: 100% (2/2), completed with 2 local objects.
To https://github.com/your-username/my-page.git
   32cd9ea..dc4f482  main -> main
Watch out

You may read about git reset --hard. It undoes the commit and deletes its changes from your files, together with any work you have not committed. That work cannot be recovered. Do not use it until you are sure you understand it.

8

“I want to undo a commit that is already on GitHub”

The reading hobby is online now, and you change your mind about it. The commit is on GitHub, so do not amend or reset it: GitHub would then have commits your computer does not, and your next push would be rejected. Instead, make a new commit that undoes it, with git revert and the commit’s hash. HEAD works too, because it is the latest commit. As with a merge, VS Code opens a tab with a ready-made message, Revert "Add reading to my hobbies": close it to accept, then click back in the terminal.

Terminal
$ git revert HEAD[main 3189807] Revert "Add reading to my hobbies"
 2 files changed, 5 deletions(-)

The reading line and the list spacing are gone from your files. Your history now has both commits, the change and its undoing, which is honest and safe:

Terminal
$ git log --oneline -33189807 (HEAD -&gt; main) Revert "Add reading to my hobbies"
dc4f482 (origin/main, origin/HEAD) Add reading to my hobbies
5841c42 Ignore my private notes$ git pushEnumerating objects: 7, done.
Counting objects: 100% (7/7), done.
Delta compression using up to 8 threads
Compressing objects: 100% (4/4), done.
Writing objects: 100% (4/4), 471 bytes | 471.00 KiB/s, done.
Total 4 (delta 2), reused 0 (delta 0), pack-reused 0 (from 0)
remote: Resolving deltas: 100% (2/2), completed with 2 local objects.
To https://github.com/your-username/my-page.git
   dc4f482..3189807  main -> main

You can revert any commit, not only the last one: use its hash from git log --oneline. A merge commit, such as a merged pull request, is the exception: to undo what a merge brought in, use git revert -m 1 HASH.

Watch out

A revert does not hide anything. The old commit stays in the history, and anyone can read the history of a public repository. If you pushed a password or a key, change it at once, on the site it belongs to. Removing it from the history is an advanced job.

9

“I think I lost a commit”

You amended a commit and reset one. Where did the old versions go? Nowhere yet. Git keeps a diary of every place HEAD has been, called the reflog:

Terminal
$ git reflog -73189807 (HEAD -&gt; main, origin/main, origin/HEAD) HEAD@{0}: revert: Revert "Add reading to my hobbies"
dc4f482 HEAD@{1}: commit: Add reading to my hobbies
5841c42 HEAD@{2}: reset: moving to HEAD~1
cab53b1 HEAD@{3}: commit (amend): Add reading to my hobbies
b0c7144 HEAD@{4}: commit: Add redaing to my hobbies
5841c42 HEAD@{5}: commit: Ignore my private notes
32cd9ea HEAD@{6}: pull: Fast-forward

Read it from the bottom up: the pull at the end of Lesson 10, then the story of this lesson. HEAD@{0} is where HEAD is now, HEAD@{1} where it was one step before, and so on. Even the commit with the typo, b0c7144, is still there. To bring back any of these commits, put a branch on it, with a hash from your own reflog:

Terminal
$ git branch rescue b0c7144

Now rescue points at that commit, and you can switch to it and look at it. You do not need to do this now. If you try it, delete the branch afterwards with git branch -D rescue (a capital D, because its commit is not merged). Git keeps such “lost” commits for at least 30 days, so rescue them soon.

10

Which undo do I need?

Situation Command Safe after pushing?
Throw away changes to a file that are not staged git restore FILE Not about commits; the changes are lost
Get a file as it was in an older commit git restore --source HASH FILE Yes: you commit the result as a new change
Take a file out of the staging area git restore --staged FILE Yes, it changes nothing in the history
Never track a file (not yet committed) add it to .gitignore Yes
Fix the last commit’s message or files git commit --amend No: only before pushing
Undo the last commit, keep the changes git reset --soft HEAD~1 No: only before pushing
Undo a commit that is on GitHub git revert HASH Yes: this is the way
Find a commit that seems lost git reflog Yes
If something went wrong

I amended or reset a commit that was already pushed, and now my push is rejected. Do not use git push --force, which many websites suggest: it replaces GitHub’s history with yours and can delete commits there. Pull (git pull), resolve any conflict as in Lesson 6, and push. Your history will have a merge commit, and nothing is lost.

git revert stopped with a conflict. Later commits changed the same lines. Resolve it as in Lesson 6, then git add the files and git revert --continue. Or give up with git revert --abort.

error: commit ... is a merge but no -m option was given. You tried to revert a merge commit. Use git revert -m 1 HASH: it undoes what the merge brought into the branch it was made on.

11

What you learned

  • Commit before anything risky; what is committed can be found again.
  • Rewrite history (--amend, reset) only for commits you have not pushed. After pushing, use git revert.
  • git restore --staged FILE unstages; .gitignore keeps files you have not committed out of Git.
  • git restore --source HASH FILE brings back an older version of a file.
  • git reflog lists everywhere HEAD has been, so “lost” commits can be found.
Command What it does
git restore --staged FILE Takes a file out of the staging area
git restore --source HASH FILE Brings back a file as it was in commit HASH
git commit --amend -m "..." Replaces the last commit, with what is staged and a new message
git reset --soft HEAD~1 Undoes the last commit and keeps its changes staged
git revert HASH Makes a new commit that undoes commit HASH
git reflog Lists every commit HEAD has pointed at
12

Check yourself

1
You committed with a typo in the message and have not pushed. What is the simplest fix?
--amend replaces the last commit. It is safe because GitHub has not seen the old one.
2
A commit with a mistake is already on GitHub. How do you undo it?
revert adds a new commit that undoes the old one, so the history GitHub has stays intact.
3
You ran git add . and staged a file with passwords in it. You have not committed. What do you do?
Unstaging keeps it out of the commit; .gitignore keeps it out of every future git add ..
4
Where can you find a commit that you replaced with --amend?
The reflog lists the commits HEAD has pointed at recently. Git keeps lost commits there for at least 30 days.
