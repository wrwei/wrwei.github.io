Module 12Verifying functional programs

Prove that a program does what its specification says, for every input. You will verify insertion sort, a binary search tree and a queue made of two lists, see why a specification needs each of its parts, and turn the verified functions into Haskell code.

⏱ 230 minYou need: Modules 1–11

In this module you will

  • Separate a specification (what a program must do) from an implementation (how it does it), and state the theorem that connects them
  • Verify insertion sort against the specification “sorted, and a permutation of the input”, finding the lemmas the proofs need
  • Explain why each half of a specification is needed, and catch weak specifications with Quickcheck and Nitpick
  • Verify a binary search tree with an invariant and an abstraction function
  • Prove a queue made of two lists correct by data refinement, and say where its invariant is needed
  • Export verified functions as Haskell code, and say what the generated code is and is not guaranteed to do

What it means to verify a program

Module 1 began with a requirement from a school’s software: “Sort the list of scores before printing it.” It turned the sentence into a formula about the input list xs and the output list ys,

sorted(ys)  ∧  mset(ys)=mset(xs),\mathit{sorted}(ys) \;\land\; \mathit{mset}(ys) = \mathit{mset}(xs), sorted(ys)∧mset(ys)=mset(xs),

and promised that a proof could show that a sorting program meets it for every input. Parts II and III gave you the tools: functions defined with fun (Module 8), automation (Module 9), structured proofs (Module 10) and the art of finding the right induction and the missing lemma (Module 11). This module puts them together and keeps the promise.

Three things are involved in every verification, and it pays to keep them apart.

Definition 12.1Implementation, specification, correctness theorem

The implementation is the program that does the work: here, a function defined with fun. It says how to compute the result.

The specification is a property that every acceptable result must have. It says what the result must be, not how to compute it.

A correctness theorem states that, for every input satisfying its stated preconditions, the result of the implementation has the specified property. A program is verified against that specification when this theorem has been proved. Sorting below has no input precondition beyond its type; the tree and queue theorems use representation invariants.

For sorting, the implementation in this module is insertion sort, a function isort. The specification is the formula above. The correctness theorem joins them:

∀xs.  sorted(isort xs)∧mset(isort xs)=mset(xs)\forall xs.\; \mathit{sorted}(\mathit{isort}\ xs) \land \mathit{mset}(\mathit{isort}\ xs) = \mathit{mset}(xs) ∀xs.sorted(isort xs)∧mset(isort xs)=mset(xs)

Why write two descriptions of the same thing? Because they serve different readers.

  • The specification is for people. It should be short and close to what was meant, so that you can check by reading it that it says the right thing. This is validation (Module 1), and it is easier the less the specification says about computation.
  • The implementation is for the computer. It should be fast, use little memory, or fit the data structures at hand. Clever implementations are hard to check by reading.
  • The proof is the bridge. A checked correctness theorem lets you rely on the specified behaviour without rechecking the algorithm by hand, provided its assumptions and trusted base apply. It does not establish properties that the specification leaves out.

One specification also serves many implementations. Insertion sort, merge sort and quicksort all meet the same sorting specification; each needs its own proof with that implementation substituted into the correctness statement.

This module uses two ways to present a specification. A property describes the result directly, as sorted and mset do for sorting. A model describes a simple version of the data and its operations, such as a mathematical set or a plain list, and the theorem says that the clever version behaves like the simple one. Sections 12.5 and 12.6 develop the second kind.

Key idea

A test checks the implementation on selected inputs. A correctness theorem covers every input under its stated preconditions, but it is only as good as its specification: a proof against a specification that says too little proves too little. Section 12.4 shows what happens when half of a specification is missing.

Good to know

The correctness in this module is functional correctness: it is about which result a program computes. How long it takes and how much memory it uses are other properties, with specifications of their own. They can be verified too, but this module does not; Section 12.6 points to a library theory that does it for one of the programs here.

Insertion sort and its specification

The program

Insertion sort is the way many people sort a hand of cards: take the cards one at a time and insert each into its place among the cards already sorted. As a recursive function it reads: to sort a list x # xs, sort the tail xs, then insert x at the right place. Inserting x into a sorted list walks along the list until it meets an element that is not smaller than x, and puts x in front of it.

Example 12.1Insertion sort on paper

Write ins x ys for inserting x into the sorted list ys, and isort for the sort. Then

isort [3,1,2]=ins 3 (ins 1 (ins 2 [ ]))=ins 3 (ins 1 [2])=ins 3 [1,2]=1#ins 3 [2]=1#2#ins 3 [ ]=[1,2,3].\begin{aligned} \mathit{isort}\ [3, 1, 2] &= \mathit{ins}\ 3\ (\mathit{ins}\ 1\ (\mathit{ins}\ 2\ [\,])) = \mathit{ins}\ 3\ (\mathit{ins}\ 1\ [2]) \\ &= \mathit{ins}\ 3\ [1, 2] = 1 \mathbin{\#} \mathit{ins}\ 3\ [2] = 1 \mathbin{\#} 2 \mathbin{\#} \mathit{ins}\ 3\ [\,] = [1, 2, 3]. \end{aligned} isort [3,1,2]​=ins 3 (ins 1 (ins 2 []))=ins 3 (ins 1 [2])=ins 3 [1,2]=1#ins 3 [2]=1#2#ins 3 []=[1,2,3].​

ins 1 [2] puts 1 in front at once, because 1 ≤ 2. ins 3 [1, 2] passes 1 and 2, because neither is at least 3, and arrives at the end of the list.

The specification

The specification has two halves, both made of library functions.

Sorted. sorted from the library says that each element of a list is at most every element after it. The library defines sorted through a more general function, sorted_wrt, so its equations are not called sorted.simps; they are the lemma sorted_simps:

Isabelle
thm sorted_simps
Output
  sorted [] = True
  sorted (?x # ?ys) = ((∀y∈set ?ys. ?x ≤ y) ∧ sorted ?ys)

The question marks mark schematic variables (Module 7): the equations hold for every x and ys. Read the second equation aloud: “x # ys is sorted if and only if x is at most every y in ys, and ys is sorted”. set ys is the set of the elements of ys, and ∀y∈set ys. P y reads “for every y in ys, P of y”. Try it on two lists:

Isabelle
value "sorted [1, 2, 2, 5 :: nat]"
value "sorted [1, 3, 2 :: nat]"
Output
"True"
  :: "bool"

"False"
  :: "bool"

A permutation. Sortedness alone is not enough, as Module 1 noticed: the empty list is sorted. The result must also contain the same elements as the input, each as often. Sets cannot say “as often”, so the specification uses multisets.

Definition 12.2Multiset and permutation

A multiset (or bag) is a collection in which order does not matter but the number of copies of each element does. mset xs, of type 'a multiset, is the multiset of the elements of the list xs; count M x is the number of copies of x in M. A list ys is a permutation of xs if it has the same elements, each as often: mset ys = mset xs.

Isabelle
value "mset [2, 1, 2 :: nat] = mset [1, 2, 2]"
value "mset [1, 2 :: nat] = mset [1, 2, 2]"
value "count (mset [2, 1, 2 :: nat]) 2"
Output
"True"
  :: "bool"

"False"
  :: "bool"

"2"
  :: "nat"

[2, 1, 2] and [1, 2, 2] are permutations of each other; [1, 2] has one 2 too few. In proofs you meet multisets through the two equations that define mset:

Isabelle
thm mset.simps
Output
  mset [] = {#}
  mset (?a # ?x) = add_mset ?a (mset ?x)

The second equation reads “the multiset of a # x is the multiset of x with one more copy of a”. {#} is the empty multiset and add_mset a M is M with one more copy of a. So mset [3, 1] = add_mset 3 (add_mset 1 {#}), which Isabelle also writes {#3, 1#}. When value computes a multiset, though, it shows it as mset of a list:

Isabelle
value "mset [3, 1 :: nat]"
Output
"mset [3, 1]"
  :: "nat multiset"

To compute with multisets, Isabelle represents each one by a list of its elements, and value prints that representation. Section 12.6 comes back to this.

Definition 12.3The sorting specification

A function f :: 'a::linorder list ⇒ 'a list meets the sorting specification if for every list xs, sorted (f xs) and mset (f xs) = mset xs: the result is sorted, and it is a permutation of the input.

Before you spend time on a proof, test the claim. Quickcheck (Module 9) tries to refute it:

Isabelle
lemma "sorted (isort xs) ∧ mset (isort xs) = mset xs"
  quickcheck
  oops
Output
Testing conjecture with Quickcheck-exhaustive...

Quickcheck found no counterexample.

Quickcheck found no counterexample within its bounds on lists and test values. A bug may need an untested case, including a longer list or different element values. With its default settings, Isabelle/jEdit also tries Auto Quickcheck on new goals and marks the line with a blue i when it finds a counterexample (Module 1). Now prove it.

Proving insertion sort correct

The correctness theorem is a conjunction, so prove its halves separately and join them at the end. Both halves follow the same plan, the one Module 11 taught: try the obvious induction, read the goal on which automation gets stuck, and find the lemma that is missing.

Sorted: the obvious attempt

isort is defined by recursion on the list, so try induction on the list:

Isabellefails on purpose
lemma "sorted (isort xs)"
  by (induction xs) auto
Output
Failed to finish proof⌂:
goal (1 subgoal):
 1. ⋀a xs. sorted (isort xs) ⟹ sorted (ins a (isort xs))

The base case is solved; the induction step is not. Read the goal that is left. Its premise is the induction hypothesis, sorted (isort xs), and its conclusion is sorted (ins a (isort xs)), where a is Isabelle’s name for the head of the list. So the step needs one fact: inserting into a sorted list gives a sorted list. That fact is about ins alone; isort only supplies the sorted list. Following Module 11’s recipe, replace the specific list isort xs by a variable, and state the fact as a lemma of its own:

sorted xs⟹sorted (ins x xs)\mathit{sorted}\ xs \Longrightarrow \mathit{sorted}\ (\mathit{ins}\ x\ xs) sorted xs⟹sorted (ins x xs)

The lemmas about ins

On paper, the lemma follows by induction on xs. For the empty list, ins x [] = [x] is sorted. For y # ys, look at the two branches of ins:

  • If x ≤ y, the result is x # y # ys. It is sorted because x ≤ y, y is at most every element of ys (the list y # ys is sorted), so x is too, and y # ys is sorted.
  • Otherwise y < x, and the result is y # ins x ys. The tail ins x ys is sorted by the induction hypothesis, because ys is sorted. And y must be at most every element of ins x ys. Which elements are those? Those of ys, and x. y is at most each of them: at most x because y < x, at most the elements of ys because y # ys is sorted.

The second branch uses a fact that is so obvious on paper that it is easy to overlook: the elements of ins x ys are x and the elements of ys. Isabelle does not overlook it. Start the proof of the lemma and look at the goals that auto leaves:

Isabelle
lemma "sorted xs ⟹ sorted (ins x xs)"
  apply (induction xs)
  apply auto
Output
proof (prove)
goal (1 subgoal):
 1. ⋀a xs xa.
       ⟦sorted (ins x xs); ∀x∈set xs. a ≤ x; sorted xs; ¬ x ≤ a;
        xa ∈ set (ins x xs)⟧
       ⟹ a ≤ xa
Isabelle
  oops

One goal remains, from the branch where ¬ x ≤ a: the head a must be at most every element xa of ins x xs. (The bound x in ∀x∈set xs. a ≤ x is a different x from the one being inserted; Isabelle reuses the name.) auto knows that a is at most every element of xs and that ¬ x ≤ a, but nothing about which elements ins x xs has: exactly the fact the paper proof used without comment. State it as a lemma. It has its own, easy induction:

Isabelle
lemma set_ins: "set (ins x xs) = insert x (set xs)"
  by (induction xs) auto

insert x A is the set A with x added, {x} ∪ A. With set_ins available, the lemma about sortedness goes through. Here it is in Isar, following the paper proof case by case:

Isabelle
lemma sorted_ins: "sorted xs ⟹ sorted (ins x xs)"
proof (induction xs)
  case Nil
  show ?case by simp
next
  case (Cons y ys)
  show ?case
  proof (cases "x ≤ y")
    case True
    with Cons.prems show ?thesis by auto
  next
    case False
    with Cons show ?thesis by (auto simp: set_ins)
  qed
qed

In the case x ≤ y, the premise Cons.prems, that y # ys is sorted, is all auto needs. In the other case it also needs the induction hypothesis (passed with the whole of Cons) and the new lemma. Once you know which facts each step needs, the whole induction fits on one line as well; the Isar version shows a reader where each fact is used.

Isabelle
lemma "sorted xs ⟹ sorted (ins x xs)"
  by (induction xs) (auto simp: set_ins)

Now the theorem’s first half is the original induction, with the lemma passed to auto:

Isabelle
lemma sorted_isort: "sorted (isort xs)"
  by (induction xs) (auto simp: sorted_ins)

A permutation

The second half goes the same way. Try the obvious induction and look at the step:

Isabelle
lemma "mset (isort xs) = mset xs"
  apply (induction xs)
  apply auto
Output
proof (prove)
goal (1 subgoal):
 1. ⋀a xs.
       mset (isort xs) = mset xs ⟹
       mset (ins a (isort xs)) = add_mset a (mset xs)
Isabelle
  oops

The step needs the multiset of ins a (isort xs). With the hypothesis mset (isort xs) = mset xs, the goal would follow from a fact about ins alone: inserting x adds one copy of x to the multiset. As before, generalise isort xs to any list:

Isabelle
lemma mset_ins: "mset (ins x xs) = add_mset x (mset xs)"
  by (induction xs) auto

lemma mset_isort: "mset (isort xs) = mset xs"
  by (induction xs) (auto simp: mset_ins)

Notice that mset_ins holds for every list, sorted or not: ins never loses or duplicates an element, wherever it stops.

The correctness theorem

The two halves give the theorem. proof without a method applies the standard rule for ∧ (Module 10), which leaves one goal for each half:

Isabelle
theorem isort_correct: "sorted (isort xs) ∧ mset (isort xs) = mset xs"
proof
  show "sorted (isort xs)" by (rule sorted_isort)
next
  show "mset (isort xs) = mset xs" by (rule mset_isort)
qed

The command theorem, like corollary (Module 11) and proposition, means the same as lemma; the word marks a main result. Insertion sort is verified: for every list of every linearly ordered type, isort returns a sorted permutation of its input.

Key idea

Proofs about programs are found from the top down and written from the bottom up. You start with the theorem, try induction, and read the goal on which automation stops; the goal tells you which lemma about a smaller function is missing, often after you generalise a specific term to a variable. The finished theory lists the lemmas first (set_ins, sorted_ins, mset_ins) and the theorem last.

Tip

When a goal mentions a library function, such as mset of an appended list, the lemma you need is probably in the library already. Search for it with find_theorems (Module 9) before you prove it yourself. For functions of your own, such as ins, the lemmas are yours to state.

Why a specification needs both halves

A verified program is only as good as its specification, so look at the specification as critically as at the program. Would one half have been enough? Two deliberately wrong “sorting” functions answer the question.

Isabelle
definition sort_drop :: "'a::linorder list ⇒ 'a list" where
  "sort_drop xs = []"

definition sort_keep :: "'a::linorder list ⇒ 'a list" where
  "sort_keep xs = xs"

sort_drop throws the list away; sort_keep returns it unchanged. Neither sorts. But sort_drop meets the first half of the specification, because the empty list is sorted:

Isabelle
lemma "sorted (sort_drop xs)"
  by (simp add: sort_drop_def)

Its failure shows only in the second half, and Quickcheck finds it at once:

Isabelle
lemma "mset (sort_drop xs) = mset xs"
  quickcheck
Output
Testing conjecture with Quickcheck-exhaustive...

Quickcheck found a counterexample:
  xs = [a1]
Evaluated terms:
  mset (sort_drop xs) = mset []
  mset xs = mset [a1]

The counterexample is a list with one element, a₁. Quickcheck tests a claim about an unknown element type on small types whose values it calls a₁, a₂, a₃ and so on. The evaluated terms show the two sides of the equation, each multiset printed as mset of a list, as value prints it: the empty multiset on the left, a multiset with a₁ on the right. Nitpick (Module 9) agrees. It tries several sizes of the element type at once, so which counterexample it reports first can vary from run to run; the option card 'a = 2 fixes the size of 'a to two values:

Isabelle
  nitpick [card 'a = 2]
Output
Nitpicking formula...

Nitpick found a counterexample for card 'a = 2:
  Free variable:
    xs = [a1]
Isabelle
  oops

sort_keep is the mirror image. It meets the second half, since every list is a permutation of itself:

Isabelle
lemma "mset (sort_keep xs) = mset xs"
  by (simp add: sort_keep_def)

and fails the first:

Isabelle
lemma "sorted (sort_keep xs)"
  quickcheck
  oops
Output
Testing conjecture with Quickcheck-exhaustive...

Quickcheck found a counterexample:
  xs = [a2, a1]

Quickcheck’s small types are ordered by the index of their values, a₁ < a₂ < a₃, so the list [a₂, a₁] is out of order, and sort_keep returns it unchanged.

Each half rules out one kind of wrong program. “Sorted” rules out programs that leave elements out of order; “permutation” rules out programs that lose, add or duplicate elements. Only together do they say what sorting means.

Are the two halves together enough, or could a wrong program still meet both? They are enough: for each input, exactly one list is sorted and a permutation of it. The library proves this about its own sorting function sort:

Isabelle
thm properties_for_sort
Output
⟦mset ?ys = mset ?xs; sorted ?ys⟧ ⟹ sort ?xs = ?ys

Read it as: if ys is a permutation of xs and ys is sorted, then ys is sort xs. So every function that meets the specification computes the same results as sort; Exercise 12.7 uses this to prove isort xs = sort xs. The specification pins down the result for every input.

Watch out

A common weakening of the specification uses sets instead of multisets: sorted ys ∧ set ys = set xs. It looks right, and it is wrong. A function that sorts and also removes duplicates, turning [2, 1, 2] into [1, 2], meets it. For scores in a school this loses a pupil’s mark whenever two pupils have the same score. Exercise 12.8 builds such a function and lets Quickcheck expose it.

Good to know

Not every specification has to pin down the result. A specification that allows several results is useful when any of them will do: “return some element of the list”, “return a shortest path”. But then “meets the specification” is all the theorem promises, and the users of the program must not rely on which result they get.

Binary search trees

Sorting is a function from inputs to outputs. Many programs instead keep data in a structure and offer operations on it: insert a key, ask whether a key is present. Such a structure is correct if the operations behave as they should on the data the structure represents. A binary search tree is the standard example.

To find a name in a sorted phone book you do not read it from the first page: you open it in the middle, see whether the name comes before or after, and repeat in the half that remains. A binary search tree stores keys so that every search can work like that. Each node holds a key; the keys in its left subtree are smaller, the keys in its right subtree larger. To look for a key, compare it with the key at the root and go left or right. A search follows a single path from the root and examines at most as many keys as the tree is high. A well-balanced tree with n keys has height proportional to log₂(n + 1). The trees implemented below are not kept balanced, so their height can be n.

Trees and the set they represent

The trees are those of Module 11: a tree is either a leaf Lf, which holds nothing, or a node Nd l x r with a left subtree l, a key x and a right subtree r. Your theory for this module needs its own copy of the datatype:

Isabelle
datatype 'a btree = Lf | Nd "'a btree" 'a "'a btree"

A search tree stands for a set of keys: the set of all keys in its nodes. This is what a user of the tree cares about. Which shape the tree has, and where each key sits, is the tree’s business. Define the set as a function:

Isabelle
fun set_of :: "'a btree ⇒ 'a set" where
  "set_of Lf = {}"
| "set_of (Nd l x r) = set_of l ∪ {x} ∪ set_of r"

set_of is the abstraction function of search trees: it maps each tree, the concrete data, to the set it represents, the abstract value. Section 12.6 makes the idea general.

Good to know

The datatype command defines such a function by itself, called set_btree, together with others such as map_btree (the Isabelle manual on datatypes, datatypes.pdf, lists them). Its equations, with variable names that Isabelle generated, say the same as those of set_of:

Isabelle
thm btree.set
Output
  set_btree Lf = {}
  set_btree (Nd ?x21.0 ?x22.0 ?x23.0) =
  set_btree ?x21.0 ∪ {?x22.0} ∪ set_btree ?x23.0

?x21.0 has the name x21 and index 0. The dot separates the index from a name ending in a digit; without it, ?x21 would mean name x with index 21 (Module 9). This module defines its own function, so that the abstraction function is visible in the theory.

Search and insertion

Searching compares the key with the key of the node and goes left, goes right, or stops:

Isabelle
fun isin :: "'a::linorder ⇒ 'a btree ⇒ bool" where
  "isin x Lf = False"
| "isin x (Nd l y r) =
     (if x < y then isin x l else if y < x then isin x r else True)"

Insertion searches in the same way. If it finds the key, the tree stays as it is; if it reaches a leaf, the key was not there, and the leaf becomes a new node:

Isabelle
fun tinsert :: "'a::linorder ⇒ 'a btree ⇒ 'a btree" where
  "tinsert x Lf = Nd Lf x Lf"
| "tinsert x (Nd l y r) =
     (if x < y then Nd (tinsert x l) y r
      else if y < x then Nd l y (tinsert x r)
      else Nd l y r)"

  :: "bool"

"False"
  :: "bool"

A set has no order: Isabelle prints the keys in the order in which the generated code collected them, and {5, 2, 1, 4, 8, 9} is the same set as {1, 2, 4, 5, 8, 9}. The search for 4 goes left at 5 and right at 2, and finds 4. The search for 7 goes right at 5, left at 8, and reaches a leaf: 7 is not there. Output
"Nd (Nd (Nd Lf 1 Lf) 2 (Nd Lf 4 Lf)) 5 (Nd (Nd Lf 6 Lf) 8 (Nd Lf 9 Lf))"
  :: "int btree"

The invariant

The search only works if the keys are in the right places. In this tree, 6 sits in the left subtree of 5, where only smaller keys belong:

Isabelle
value "isin 6 (Nd (Nd Lf 1 (Nd Lf 6 Lf)) 5 (Lf :: int btree))"
Output
"False"
  :: "bool"

The key 6 is in the tree, but the search goes right at 5 and finds a leaf. The functions are not wrong; they assume something about the tree that this tree does not satisfy. That assumption is the tree’s invariant.

Definition 12.4Invariant of a data structure

An invariant of a data structure is a property that every value built by its operations has, and that the operations may rely on. The operations must preserve it: if their input satisfies the invariant, so does their output.

For search trees, the invariant is that at every node, all keys of the left subtree are smaller than the node’s key and all keys of the right subtree are larger:

Isabelle
fun bst :: "'a::linorder btree ⇒ bool" where
  "bst Lf = True"
| "bst (Nd l x r) =
     (bst l ∧ bst r ∧ (∀y ∈ set_of l. y < x) ∧ (∀y ∈ set_of r. x < y))"

∀y ∈ set_of l. y < x reads “every key y of l is less than x”. Check it on the two trees:

Isabelle
value "bst t0"
value "bst (Nd (Nd Lf 1 (Nd Lf 6 Lf)) 5 (Lf :: int btree))"
Output
"True"
  :: "bool"

"False"
  :: "bool"

The specification of search trees now has three parts, and Section 12.6 shows that they are an instance of a general pattern:

  1. Insertion preserves the invariant: bst t ⟹ bst (tinsert x t).
  2. Insertion inserts: set_of (tinsert x t) = insert x (set_of t).
  3. Search is correct: bst t ⟹ isin x t = (x ∈ set_of t).

The second and third parts say that tinsert and isin do to the tree what insert and ∈ do to the set it represents. The third holds only for trees that satisfy the invariant, as the tree with 6 in the wrong place showed.

The empty tree Lf also needs to satisfy the invariant and represent the empty set. Both follow from the definitions; Section 12.6 includes initialisation explicitly in the general pattern.

A wrong invariant

The invariant must say the right thing, and that is easy to get wrong. A tempting simplification compares each node only with its two children: the left child’s key must be smaller, the right child’s larger. It is easier to state and quicker to check:

Isabelle
fun bst_local :: "'a::linorder btree ⇒ bool" where
  "bst_local Lf = True"
| "bst_local (Nd l x r) =
     (bst_local l ∧ bst_local r ∧
      (case l of Lf ⇒ True | Nd _ y _ ⇒ y < x) ∧
      (case r of Lf ⇒ True | Nd _ y _ ⇒ x < y))"

The pattern Nd _ y _ matches any node and names only its key; _ stands for a part you do not need. Is search correct for trees with this invariant? Ask Quickcheck before trying to prove it:

Isabelle
lemma "bst_local t ⟹ isin x t = (x ∈ set_of t)"
  quickcheck
Output
Testing conjecture with Quickcheck-exhaustive...

Quickcheck found a counterexample:
  t = Nd Lf a2 (Nd (Nd Lf a1 Lf) a3 Lf)
  x = a1
Evaluated terms:
  isin x t = False
  x ∈ set_of t = True
Isabelle
  oops

Draw the tree. Its root holds a₂ and has an empty left subtree. The right child holds a₃, and the left child of that node holds a₁. Each node is in order with its children: a₃ is larger than a₂, and a₁ is smaller than a₃. So bst_local holds. But a₁ is smaller than a₂ and sits in a₂’s right subtree. The search for a₁ compares it with a₂, goes left and finds a leaf: isin answers False, although a₁ is in the tree. The evaluated terms show exactly this.

Watch out

An invariant about a recursive structure usually has to speak about whole subtrees, not only about neighbours. If a property holds between neighbours only, check with Quickcheck or Nitpick that it implies what the operations need, before you build proofs on it.

Proving the search tree correct

Start with the first part of the specification, the invariant, and try the obvious induction:

lemma "bst t ⟹ bst (tinsert x t)"
  apply (induction t)
  apply auto

proof (prove)
goal (2 subgoals):
 1. ⋀t1 x2 t2 xa.
       ⟦bst (tinsert x t1); bst (tinsert x t2); bst t1; bst t2;

Two goals remain, one for each direction in which tinsert descends. Look at the first: insertion went right (x2 < x, where x2 is the key at the node), and the goal asks that x2 be smaller than every key xa of tinsert x t2. The premises say that x2 is smaller than every key of t2 and smaller than x. That would be enough if auto knew that the keys of tinsert x t2 are x and the keys of t2, which is the second part of the specification. Prove it first, and pass it to auto:

Isabelle
lemma set_of_tinsert: "set_of (tinsert x t) = insert x (set_of t)"
  by (induction t) auto

lemma bst_tinsert: "bst t ⟹ bst (tinsert x t)"
  by (induction t) (auto simp: set_of_tinsert)

The lemma set_of_tinsert is the second part of the specification. It plays the role that set_ins played for insertion sort: the invariant talks about the keys in subtrees, so preserving it requires knowing which keys insertion adds.

The third part, correctness of search, needs no new lemma. Try the obvious induction:

Isabelle
lemma isin_set_of: "bst t ⟹ isin x t = (x ∈ set_of t)"
  by (induction t) auto

It works at once. It is still worth knowing why it holds, because the argument shows where the invariant is needed. On paper: take a tree Nd l y r that satisfies the invariant, and compare x with y. There are three cases.

  • x < y. The search continues in l, and by the induction hypothesis it answers whether x ∈ set_of l. That is the right answer, because x cannot be y, and x cannot be in r, whose keys are all larger than y.
  • x = y. The search stops and answers True, which is right.
  • y < x. The mirror image of the first case.

The invariant is used twice in each of the outer cases: once for the induction hypothesis, which needs the subtree to be a search tree, and once to rule out the other subtree. auto found both uses by itself, because the definition of bst is a simplification rule.

Data refinement

The search tree was verified in a particular way. Its specification did not describe trees at all; it described sets, and the proofs related the tree operations to set operations through the abstraction function. This way of verifying a data structure is called data refinement, and it applies to almost every data structure.

The pattern

Definition 12.5Data refinement

This module uses data refinement with deterministic operations and an abstraction function. An abstract model is a simple mathematical type with operations whose meaning is clear, such as sets with {}, insert and ∈. A concrete data structure implements it with a type and operations of its own, chosen for efficiency. They are connected by an abstraction function α, which maps each concrete value to the abstract value it represents, and an invariant I on concrete values. The concrete structure refines the model if:

  1. the concrete empty value represents the abstract one and satisfies I;
  2. every concrete operation preserves I when its preconditions hold;
  3. on values that satisfy I and the operation’s preconditions, every concrete operation corresponds to its abstract one: applying the concrete operation and then α gives the same as applying α and then the abstract operation; and every query gives the answer its abstract query gives.

Condition 3 is often drawn as a square, as in Figure 12.3: going along the top and then down gives the same result as going down and then along the bottom. Diagrams of this kind are called commuting squares.

For search trees the pieces are:

Abstract model Concrete structure
Values 'a set 'a btree satisfying bst
Empty {} Lf
Insert insert x A tinsert x t
Member x ∈ A isin x t
Connection α = set_of, I = bst

set_of Lf = {} and bst Lf hold by the definitions, bst_tinsert is condition 2, and set_of_tinsert and isin_set_of are condition 3.

The reward comes when you use the data structure. A program that uses search trees can be reasoned about with sets, which you know well, instead of with trees. Here is a fact about trees proved without looking at a single tree, from the three lemmas alone:

Isabelle
lemma "bst t ⟹ isin y (tinsert x t) = (y = x ∨ isin y t)"
  by (simp add: bst_tinsert isin_set_of set_of_tinsert)

The simplifier turns both sides into statements about set_of t, where the claim is a law of sets. The proof never looks inside isin or tinsert: if you replaced the trees by balanced trees with the same three lemmas, this proof would not change.

A queue made of two lists

A queue is a waiting line: elements join at the back and leave from the front, so the first to join is the first to leave. The abstract model is a list, with the front of the queue at the head of the list. Joining is xs @ [x]. Leaving is tl xs, the tail of the list: the list without its first element. The element at the front is hd xs, the head of the list. In Isabelle tl [] = [], while hd [] has no specified value (Module 8).

As a program, the plain list is slow: xs @ [x] copies the whole list, so a queue of n elements costs n steps for each element that joins. A classic functional implementation uses two lists. The front list holds the first elements, in order; the back list holds the last elements in reverse order, so that joining the queue puts an element at the head of the back list in one step. Elements leave from the head of the front list. When the front list runs empty, the back list is reversed and becomes the new front list.

Isabelle
datatype 'a queue = Queue "'a list" "'a list"

A value Queue f b has the front list f and the back list b. The queue it represents is the front list followed by the back list reversed. That is the abstraction function:

Isabelle
fun list_of :: "'a queue ⇒ 'a list" where
  "list_of (Queue f b) = f @ rev b"
Isabelle
value "list_of (Queue [1, 2] [4, 3 :: nat])"
Output
"[1, 2, 3, 4]"
  :: "nat list"

Now the operations. refill moves the back list to the front when the front list is empty; enq (enqueue) adds an element at the back, deq (dequeue) removes the front element, and first returns it.

Isabelle
definition qempty :: "'a queue" where
  "qempty = Queue [] []"

fun refill :: "'a queue ⇒ 'a queue" where
  "refill (Queue [] b) = Queue (rev b) []"
| "refill q = q"

fun enq :: "'a ⇒ 'a queue ⇒ 'a queue" where
  "enq x (Queue f b) = refill (Queue f (x # b))"

fun deq :: "'a queue ⇒ 'a queue" where
  "deq (Queue [] b) = Queue [] b"
| "deq (Queue (x # f) b) = refill (Queue f b)"

fun first :: "'a queue ⇒ 'a" where
  "first (Queue f b) = hd f"

The second equation of refill applies only when the first does not, that is, when the front list is not empty (Module 8 explained how fun resolves overlapping patterns). Try the operations:

Isabelle
value "enq 5 (Queue [1, 2] [4, 3 :: nat])"
value "deq (Queue [1] [4, 3, 2 :: nat])"
Output
"Queue [1, 2] [5, 4, 3]"
  :: "nat queue"

"Queue [2, 3, 4] []"
  :: "nat queue"

Adding 5 puts it at the head of the back list. Removing 1 empties the front list, so refill reverses the back list into the front: [4, 3, 2] becomes [2, 3, 4]. Along one sequence starting at qempty, using each operation’s result as the next queue, each enqueued element is reversed from back to front at most once. This gives constant amortised list-processing cost per operation: the total cost of m operations is proportional to m, although one deq can take linear time. This is not a probability or a bound for each call. Reusing an older queue version can repeat the same reversal. The cost model and a proof of amortised bounds are separate from the functional proof here; Queue_2Lists, described below, develops such bounds.

first returns the head of the front list. That is the right answer only if the front list is empty only when the whole queue is: otherwise the first element might be waiting in the back list. The operations keep this true, because refill never leaves an empty front list in front of a non-empty back list. It is the invariant of the queue:

Isabelle
fun qinv :: "'a queue ⇒ bool" where
  "qinv (Queue f b) = (f = [] ⟶ b = [])"

Proving the queue correct

The specification follows the pattern of Definition 12.5, with lists as the abstract model:

Abstract model Queue
Empty [] qempty
Join at the back xs @ [x] enq x q
Leave at the front tl xs deq q
Front element hd xs first q
Connection α = list_of, I = qinv

Start with the empty queue, which needs only the definition of qempty:

Isabelle
lemma list_of_qempty: "list_of qempty = []"
  by (simp add: qempty_def)

Next, enq. A queue is always of the form Queue f b, so split the proof into that one case with cases q (Module 10) and try auto:

Isabelle
lemma "list_of (enq x q) = list_of q @ [x]"
  apply (cases q)
  apply auto
Output
proof (prove)
goal (1 subgoal):
 1. ⋀x1 x2.
       q = Queue x1 x2 ⟹
       list_of (refill (Queue x1 (x # x2))) = x1 @ rev x2 @ [x]
Isabelle
  oops

cases q names the two lists of the queue x1 and x2. auto has unfolded enq on the left and list_of q on the right, but it is stuck at list_of (refill (Queue x1 (x # x2))). The equations of refill depend on whether the front list x1 is empty, and auto does not split on that by itself. You could tell it to, but there is a better way: state once and for all what refill does to the list a queue represents, namely nothing. That lemma will serve every operation that calls refill:

Isabelle
lemma list_of_refill: "list_of (refill q) = list_of q"
  by (cases q rule: refill.cases) auto

lemma list_of_enq: "list_of (enq x q) = list_of q @ [x]"
  by (cases q) (simp add: list_of_refill)

cases q rule: refill.cases splits the proof into the cases of the equations of refill: a queue with an empty front list, and one with a non-empty front list. It is the case analysis that follows a function’s patterns, as rule: f.induct is the induction that follows its recursion (Module 11). Note that list_of_enq has no premise: enq is correct on every queue, invariant or not, because it only ever adds to the back.

Is deq correct on every queue too? Ask Quickcheck before proving:

Isabelle
lemma "list_of (deq q) = tl (list_of q)"
  quickcheck
Output
Testing conjecture with Quickcheck-exhaustive...

Quickcheck found a counterexample:
  q = Queue [] [a1]
Evaluated terms:
  list_of (deq q) = [a1]
  tl (list_of q) = []
Isabelle
  oops

The queue Queue [] [a₁] has an empty front list and one element in the back list. It represents the list [a₁], so removing the front element should leave the empty list. But deq sees an empty front list and returns the queue unchanged. This queue breaks the invariant, and no sequence of enq and deq starting from qempty builds it. So the correspondence for deq holds only under the invariant, and the invariant is needed exactly when the front list is empty. The Isar proof makes that visible:

Isabelle
lemma list_of_deq:
  assumes "qinv q"
  shows "list_of (deq q) = tl (list_of q)"
proof (cases q)
  case (Queue f b)
  show ?thesis
  proof (cases f)
    case Nil
    with Queue assms have "b = []" by simp
    with Nil Queue show ?thesis by simp
  next
    case (Cons x f')
    with Queue show ?thesis by (simp add: list_of_refill)
  qed
qed

With an empty front list, the invariant says that the back list is empty too, so the queue is empty and deq correctly leaves it as it is, since tl [] = []. With a non-empty front list, deq removes its head, and refill does not change the list. The remaining parts are short:

Isabelle
lemma first_correct: "qinv q ⟹ list_of q ≠ [] ⟹ first q = hd (list_of q)"
  by (cases q) auto

lemma qinv_refill: "qinv (refill q)"
  by (cases q rule: refill.cases) auto

lemma qinv_qempty: "qinv qempty"
  by (simp add: qempty_def)

lemma qinv_enq: "qinv (enq x q)"
  by (cases q) (simp add: qinv_refill)

lemma qinv_deq: "qinv q ⟹ qinv (deq q)"
  by (cases q rule: deq.cases) (auto simp: qinv_refill)

first_correct has two premises: the invariant, and that the queue is not empty. An empty queue has no front element: in the model, hd [] has no specified value. So the specification promises nothing about first on an empty queue, and leaves an implementation free to return anything there. (This implementation happens to return hd [] for the empty queue, so this particular proof would also work without the second premise.)

The lemmas qinv_qempty, qinv_enq and qinv_deq say that every queue built from qempty with enq and deq satisfies the invariant, so the premise qinv q of list_of_deq and first_correct holds for queues constructed through those operations. Calling first_correct also requires non-emptiness.

Verified data structures in practice

Search trees and queues are textbook examples, but the pattern is the one used for verified software in general.

  • Isabelle’s own library. The Isabelle distribution contains the session HOL-Data_Structures, a collection of verified functional data structures (in the folder src/HOL/Data_Structures of your Isabelle installation). Its theory Queue_Spec states the queue specification of this section, with an emptiness test as well (Exercise 12.6): eight properties, with an abstraction function list and an invariant invar. Queue_2Lists proves them for a two-list queue and establishes amortised bounds in an explicit operation-cost model. Set_Specs states the set specification of Section 12.5, with deletion as well, and theories such as Tree_Set, AVL_Set and RBT_Set prove it for unbalanced, AVL and red-black trees.
  • The code generator. When Isabelle generates code for sets, it represents a finite set by a list of its elements, a data refinement built into the library; importing HOL-Library.RBT_Set switches to red-black trees. Multisets are represented by lists too, which is why value printed mset [3, 1] in Section 12.2.
  • Large systems. The seL4 proof (Module 1) is a refinement proof on a large scale: it shows that the kernel’s C code refines an executable specification, which in turn refines an abstract specification of what the kernel does.
Key idea

Data refinement separates two questions: what a data structure means (the abstract model) and how it is built (the concrete structure). The abstraction function connects them, and the invariant records what the concrete operations assume. Programs that use the structure are reasoned about with the model only.

From verified functions to running code

Module 8 showed how export_code translates HOL functions into Standard ML, OCaml, Haskell or Scala. Applied to verified functions, it turns them into verified programs, with a guarantee that the end of this section makes precise. Export everything this module has verified, as one Haskell module. One addition first: Haskell code that uses search trees needs an empty tree to start from, so give the empty tree a name of its own (the reason for not using Lf follows below):

Isabelle
definition tempty :: "'a btree" where
  "tempty = Lf"

export_code isort tempty isin tinsert qempty enq deq first
  in Haskell module_name Verified
Output
See theory exports

As in Module 8, the Output panel only says where the code went: Isabelle stores generated code as theory exports, files that belong to the theory, instead of printing it. In Isabelle/jEdit, theory exports in the message is a link. Click it, and the File Browser opens the folder of code exported by your theory, under the virtual address isabelle-export:. There, the folder export1 holds the file Verified.hs: export_code numbers the exports of a theory export1, export2, … unless you name the folder yourself with the option file_prefix.

Open Verified.hs and you find your theory again, in Haskell. The datatypes have become Haskell data declarations: Btree with the constructors Lf and Nd, and Queue with the constructor Queue. Each function has the equations that fun derived from yours, with # written : and rev written reverse, and the functions that the exported ones need are there too: ins, refill and the library’s hd. The comparisons ≤ and < have become less_eq and less, the operations of a Haskell type class Ord that Isabelle generates from its own class ord; the classes preorder, order and linorder become Haskell classes too (Module 8 compared type classes with Haskell’s). The first lines of the module list what it exports: the functions, the class Linorder, and the types Btree and Queue without their constructors.

For this Haskell export, export_code exposes the functions in its list and, without their constructors, the datatypes and classes that these functions use directly. It exports the constructors of a datatype only when the list names one of them. Hiding constructors protects the representation: ordinary clients can construct finite, defined trees through tempty and tinsert, and queues through qempty, enq and deq, preserving the proved invariants. This does not enforce operation preconditions such as a non-empty queue for first. Had the list named the constructor Lf instead of tempty, Isabelle would have exported the type Btree with all its constructors, Nd included, and with them the power to build any tree at all.

One more thing stays inside the module: the classes Ord, Preorder and Order on which Linorder builds. As exported here, other Haskell code cannot say how to compare the elements of its own types, so it cannot yet call isort or the tree functions. Writing export_code open … exports everything: the classes with their operations, and the datatypes with their constructors. Then the functions can be used on any type, but the protection of the invariants is gone. Choosing what to export is part of designing the interface of verified code.

What is guaranteed

Every function in the generated module comes from equations that are theorems in the logic: for your own functions, the equations of your fun and definition commands (Module 8). The code generator translates each equation into an equation of the target language and adds the definitions it needs from the library. So when the generated isort returns a list, that list is the value of isort in the logic, under the trusted-base assumptions below, and the correctness theorem says that it is sorted and a permutation of the input. This guarantee, that every result the program produces is a result the logic agrees with, is called partial correctness (Module 8): it speaks about the results the program returns, not about whether it returns at all. The generated first, for example, stops with an error on an empty queue, because the library’s hd has no equation for []. The non-empty precondition excludes that call from first_correct; partial correctness alone would not promise a result in any case. The correspondence concerns inputs and defined results representing HOL values. Haskell also admits undefined and infinite lists, which do not represent values of HOL’s finite-list datatype.

What the guarantee rests on is the trusted base of Module 1, enlarged by the steps after the proof:

  • The code generator. Its translation of equations into the target language happens outside the kernel. Isabelle’s code generation manual (codegen.pdf) explains that the last steps, translation and printing, are carried out outside the logic and are kept as thin as possible, so that there is little code to trust. Little is not nothing.
  • The target compiler and its run-time system: the Haskell compiler, its libraries, garbage collector and integer arithmetic.
  • The machine: the hardware, the operating system, and limits that the logic does not know about. In the logic isort works on lists of any length; a real computer runs out of memory or stack at some length.
  • The code around it. The theorems about isin, deq and first assume the invariants bst and qinv; first_correct also requires a non-empty queue. Constructor hiding preserves representation invariants for finite, defined values built through the interface. Editing the generated code, exposing constructors or bypassing the type system can invalidate that reasoning. In the same way, the theorems about isort and the tree functions assume that ≤ and < form a linear order. After export_code open, other code compares the elements of its own types with operations that it supplies, and nothing checks that they obey the laws of linorder.
  • The specification. A verified function does what its specification says. Whether that is what the users need is still validation.
Good to know

Some correspondences between HOL and the target language are set up by hand, and they belong to the trusted base as well. Even the default set-up has a few: the generated code uses Haskell’s own lists, Booleans and reverse. Library theories such as HOL-Library.Code_Target_Nat, which Module 8 mentioned, add more: they make the generated code use the target language’s own integers instead of a datatype of natural numbers. Haskell’s Integer uses arbitrary precision, subject to resource limits; the kernel does not check this implementation. Inputs representing HOL natural numbers must still be non-negative: an arbitrary negative Integer supplied by calling code is not a natural-number value.

What you learned

  • To verify a program is to prove a correctness theorem: for every input satisfying its preconditions, the result of the implementation (how) has the property of the specification (what). The specification is written for people to read and validate; the implementation for the computer.
  • Insertion sort meets the sorting specification: sorted (isort xs) ∧ mset (isort xs) = mset xs. mset from HOL-Library.Multiset turns a list into the multiset of its elements; mset ys = mset xs says that ys is a permutation of xs.
  • Proofs about programs are found from the top down: try induction, read the goal on which auto stops, generalise it into a lemma about a smaller function (set_ins, sorted_ins, mset_ins), and prove that first.
  • Each half of a specification rules out its own kind of wrong program: [] is sorted, and the input itself is a permutation. Test specifications with Quickcheck and Nitpick before proving, and test them against deliberately wrong programs. Sets instead of multisets would let duplicates disappear.
  • A binary search tree is verified with an abstraction function (set_of) and an invariant (bst): insertion preserves the invariant and inserts into the set, and search answers membership in the set. An invariant that compares only neighbours is too weak.
  • Data refinement is the general pattern: a concrete structure, an abstract model, an abstraction function and an invariant, with the concrete operations corresponding to the abstract ones. The two-list queue refines lists, and needs its invariant for deq and first.
  • export_code turns verified functions into code, stored as theory exports. The generated code is partially correct relative to the proved equations; the code generator, the compiler, the machine and the calling code remain in the trusted base. Hiding constructors protects representation invariants for defined values built through the interface; callers still have to meet operation preconditions.

Exercise 12.4★★Sorting keeps the length

Prove length (isort xs) = length xs in two ways.

  1. By induction, with a lemma about the length of ins x xs.
  2. Without induction, from mset_isort. The number of elements of a multiset M, counted with their copies, is size M. Use find_theorems to find a library fact that relates size (mset xs) to the length of xs.
Show solution

  1. The lemma and the induction:

    Isabelle
    lemma length_ins: "length (ins x xs) = Suc (length xs)"
  by (induction xs) auto

lemma "length (isort xs) = length xs"
  by (induction xs) (auto simp: length_ins)

  2. Search for facts about the size of mset xs; the underscore stands for any term:

    Isabelle
    find_theorems "size (mset _)"
    Output
    find_theorems
  "size (mset _)"

found 1 theorem(s):
  Multiset.size_mset: size (mset ?xs) = length ?xs

    size_mset is a simp rule, so simp turns the sizes into lengths:

    Isabelle
    lemma "length (isort xs) = length xs"
proof -
  have "size (mset (isort xs)) = size (mset xs)" by (simp add: mset_isort)
  then show ?thesis by simp
qed

Exercise 12.5★★A bug in insertion

A colleague’s insertion has a bug:

Isabelle
fun ins_bad :: "'a::linorder ⇒ 'a list ⇒ 'a list" where
  "ins_bad x [] = [x]"
| "ins_bad x (y # ys) = (if x ≤ y then x # ys else y # ins_bad x ys)"

fun isort_bad :: "'a::linorder list ⇒ 'a list" where
  "isort_bad [] = []"
| "isort_bad (x # xs) = ins_bad x (isort_bad xs)"

Find the bug by reading. Then test each half of the specification with Quickcheck. Which half catches the bug, and why does the other not?

Show solution

In the case x ≤ y, ins_bad returns x # ys and forgets y. Quickcheck finds no counterexample to the first half:

  quickcheck
  oops
Output

Quickcheck found no counterexample.

but refutes the second:

  quickcheck

Quickcheck found a counterexample:

Evaluated terms:
  mset (isort_bad xs) = mset [a1]

Exercise 12.7★★★The specification determines the result

Prove isort xs = sort xs, where sort is the library’s sorting function. Use properties_for_sort (Section 12.4) with mset_isort and sorted_isort, and no induction.

Show solution

properties_for_sort concludes sort xs = ys from mset ys = mset xs and sorted ys. With ys = isort xs, its two premises are exactly mset_isort and sorted_isort, in this order, so rule can use them as the facts that discharge the premises:

Isabelle
lemma isort_sort: "isort xs = sort xs"
proof -
  have "sort xs = isort xs"
    using mset_isort sorted_isort by (rule properties_for_sort)
  then show ?thesis by simp
qed

The proof never looks at how isort works. Any function with the two properties is equal to sort, so this lemma could be proved for merge sort or quicksort in the same way.

Exercise 12.8★★★Tree sort and a weak specification

Sort a list by inserting its elements into a search tree and reading the tree from left to right:

Isabelle
fun inorder :: "'a btree ⇒ 'a list" where
  "inorder Lf = []"
| "inorder (Nd l x r) = inorder l @ [x] @ inorder r"

fun build :: "'a::linorder list ⇒ 'a btree" where
  "build [] = Lf"
| "build (x # xs) = tinsert x (build xs)"

definition tsort :: "'a::linorder list ⇒ 'a list" where
  "tsort xs = inorder (build xs)"
  1. Prove that tsort meets the weak specification of Section 12.4: sorted (tsort xs) ∧ set (tsort xs) = set xs. You need lemmas about set (inorder t), sorted (inorder t), bst (build xs) and set_of (build xs); the library lemma sorted_append describes when an appended list is sorted.
  2. Show with Quickcheck that tsort does not meet the sorting specification, and explain why.
Show solution

  1. Four lemmas, then the claim:

    Isabelle
    lemma set_inorder: "set (inorder t) = set_of t"
  by (induction t) auto

lemma sorted_inorder: "bst t ⟹ sorted (inorder t)"
  by (induction t)
     (auto simp: sorted_append set_inorder intro: less_imp_le less_trans)

lemma bst_build: "bst (build xs)"
  by (induction xs) (auto simp: bst_tinsert)

lemma set_of_build: "set_of (build xs) = set xs"
  by (induction xs) (auto simp: set_of_tinsert)

lemma "sorted (tsort xs) ∧ set (tsort xs) = set xs"
  by (simp add: tsort_def sorted_inorder bst_build set_inorder set_of_build)

    sorted_inorder is the hard one. With sorted_append and set_inorder alone, auto stops at a goal x ≤ xa for a key x of the left subtree and a key xa of the right subtree. Its premises say that every key of the left subtree is smaller than the key x2 at the node and every key of the right subtree is larger, so x < x2 and x2 < xa, but auto does not chain the two. The library rules less_trans (from x < y and y < z conclude x < z) and less_imp_le (from x < y conclude x ≤ y), given to auto with intro: (Module 9), supply the missing steps.

  2. Quickcheck refutes the sorting specification at once:

    Isabelle
    lemma "mset (tsort xs) = mset xs"
  quickcheck
  oops
    Output
    Testing conjecture with Quickcheck-exhaustive...

Quickcheck found a counterexample:
  xs = [a1, a1]
Evaluated terms:
  mset (tsort xs) = mset [a1]
  mset xs = mset [a1, a1]

    A search tree stores a set: tinsert leaves the tree unchanged when the key is already there. So tsort removes duplicates. It satisfies the weak specification with sets, which is exactly why that specification is too weak.
